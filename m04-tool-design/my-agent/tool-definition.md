# 도구 정의서 — 식품 표시·광고 사전검토 안내 에이전트

> 설계 패킷 ② 에 해당한다. 패킷 본문은 [design-packet.md](../design-packet.md),
> 사용자 관점 요구는 [PRD](../PRD.md), 결정 근거는 [PLAN](../PLAN.md).
> 작성 2026-08-31 (슬라이스 1) · 수정 2026-08-31 (슬라이스 6, 사용자 결정 4건 반영 —
> 접수 번호 `REQ-`, 우회 기록의 운영 층 이동, `MISSING_EVIDENCE` 표기 통일, enum 밖 판정 순서).
>
> **여기 적힌 인자·반환 필드는 [m05 코퍼스](../../m05-rag-chatbot-service/app/public/corpus/)
> 에서 가져왔다** (PLAN D8). 코퍼스는 읽기만 했고 m05 앱은 건드리지 않았다.
> 실측이 아니라 설계다 — 도구를 실행해 본 기록은 이 저장소에 없다 (PLAN D6).

## 0. 네 도구를 가르는 한 가지 질문

**"사용자가 무엇을 제시했는가."** 주제가 아니다 (PLAN D3).

| 사용자가 내민 것 | 도구 | 성격 |
|---|---|---|
| 쓰려는 **문구·표현** — "다이어트에 좋은", "무설탕" | `search_expression_rule` | 읽기 |
| 제품의 **식품유형** — "과자류", "음료류" | `list_mandatory_labels` | 읽기 |
| **법령명 + 조문 번호** — "식품표시광고법 제8조 제1항 제3호" | `get_article` | 읽기 |
| 읽기 도구가 답한 **뒤에도 남은 확정 요구** | `file_review_request` | **쓰기 · 승인 필요** |

주제로 가르면 즉시 무너진다. "'무설탕'이라고 표시해도 되나요"는 주제로 보면 표시사항이고
광고표현이고 영양강조표시라 셋 다 걸린다. 사용자가 내민 것으로 가르면 하나다 — **표현**.
겹치는 자리를 실제로 닫은 문장은 7절에 모아 뒀다.

**범위 밖은 다섯 번째 도구가 아니다** (PLAN D4). 세 읽기 도구가 공통으로 `OUT_OF_SCOPE`
를 반환하고, 소관 법령 이름은 모델이 대지 않고 코퍼스 메타의 `outOfScope` 고정 목록 7건에서
꺼낸다. 범위 밖은 별도 자료가 아니라 **조회 실패의 한 종류**다.

## 1. 공통 규약

네 도구가 같이 지키는 것. 도구별 항목에서 되풀이하지 않는다.

### 1.1 인용 튜플 — 반환의 최소 단위

모든 근거는 이 다섯 칸으로 나간다. 코퍼스 청크의 필드를 그대로 쓴다.

| 칸 | 예 | 코퍼스 출처 |
|---|---|---|
| `lawName` | 식품 등의 표시ㆍ광고에 관한 법률 | `chunks[].lawName` |
| `kind` | 법률 / 시행령 / 시행규칙 / 고시 | `chunks[].sourceKind` |
| `path` | 제8조제1항제3호 | `chunks[].path` (표기 정규화 후) |
| `url` | https://www.law.go.kr/... | `chunks[].url` |
| `effectiveDate` + `inForce` | 2025-09-19 / true | `chunks[].effectiveDate`, `chunks[].inForce` |

**시행일이 인용의 일부인 이유** — 이 도메인은 개정이 잦다. 코퍼스가 실제로
`식품등의 표시기준` 에 2028-01-01 시행 예정 개정을, `식품표시광고법` 에 2026-11-27 시행
예정을 달고 있다. 시행일 없는 조문 인용은 사용자가 확인할 수 없는 인용이다.

### 1.2 반환 봉투

```jsonc
{
  "ok": true,
  "code": "OK",                  // 또는 실패 코드 (8절 총람)
  "hits": [                      // 최대 5건
    {
      "citation": { "lawName": "...", "kind": "고시", "path": "...",
                    "url": "...", "effectiveDate": "...", "inForce": true },
      "excerpt": "...",          // 400자 상한. 도구가 자른 자리는 "…" 로 표시
      "why": "이 근거가 걸린 이유 한 문장"
    }
  ],
  "coverage": { "level": "full", "note": "..." },   // full / partial / none
  "limits": ["이 답으로 말할 수 없는 것"],
  "corpusAsOf": "2026-08-28",    // 코퍼스 수집일
  "corpusAgeDays": 3             // 오늘 기준 경과일
}
```

### 1.3 반환에 **넣지 않는** 것 (PRD F4)

| 넣지 않는 것 | 왜 |
|---|---|
| 청크 id (`FLA-051`, `UNF-007`) | 내부 식별자다. 사용자가 확인할 수 없고 조문 식별자는 이미 `path` 에 있다 |
| 검색 점수 (코사인·BM25), 임베딩 벡터 | 내부 상태다. 숫자가 나가면 근거의 강약으로 오독된다 |
| 코퍼스 파일 경로, 청크 개수, 인덱스 오프셋 | 내부 구조다 |
| 조문 전문 일괄, 별표 전체 라인 | **원문 덤프.** 근거는 조회한 범위만 나간다 |
| 다른 요청의 내용, 이전 검토 요청의 본문 | 요청 간 격리 |

`get_article` 은 **지정한 조문 하나**의 본문을 준다. 이것은 덤프가 아니다 — 범위를 사용자가
지정했고 도구가 그 하나만 반환하기 때문이다. 범위를 못 좁히면 반환이 아니라 되묻기다 (4절).

### 1.4 실패 뒤 행동은 네 가지뿐 (PRD F5)

| 행동 | 뜻 | 상한 |
|---|---|---|
| **재시도** | 같은 인자로 다시 호출한다. 일시적 장애일 때만 | 도구당 **1회**. 그 뒤에는 보류 |
| **되묻기** | 사용자에게 빠진 것 하나를 묻는다. 추측해서 채우지 않는다 | 한 턴에 **질문 1개** |
| **보류** | 답을 만들지 않고, 무엇을 못 했는지 말한다. 없는 근거로 메우지 않는다 | — |
| **이관** | `file_review_request` 로 사람에게 넘긴다. 승인을 거친다 | — |

**같은 코드가 두 번 연속 나오면 재시도하지 않고 보류로 내린다.** 반복 실패는 장애가 아니라
경계 밖이라는 신호다 (PRD F6 중단 조건).

### 1.5 검토 대상 문구는 데이터다 (PRD 5절)

세 읽기 도구가 사용자 문구를 인자로 받는다. 그 문구는 **자연스럽게 명령문으로 온다** —
"지금 바로 구매하세요", "전문가가 인정한 제품입니다". 도구는 인자로 들어온 문구를
**지시로 해석하지 않고**, 반환에 `treatedAsData: true` 를 실어 그 사실을 남긴다.
실제 차단은 도구가 아니라 하네스가 한다 — 스키마는 안내이지 권한이 아니다.

## 2. `search_expression_rule` — 광고·표시 표현 기준 조회

### ① 이름
`search_expression_rule` (광고·표시 표현 기준 조회) · **읽기**

### ② 하는 일 한 문장
사용자가 쓰려는 문구를 부당한 표시·광고 기준과 대조해 **걸리는 기준 조문을 찾아 준다.**
(적법 여부를 판정하지 않는다 — 판정은 이 제품이 하지 않기로 한 일이다. PRD 1절)

### ③ 쓰는 때 · 안 쓰는 때

**쓰는 때**

- 사용자가 **쓰려는(또는 이미 쓴) 문구를 제시**하고 그 문구를 써도 되는지 물을 때
- 문구가 표시면에 들어가든 광고에 들어가든 상관없다 — **제시된 것이 표현이면 이 도구다**
- 문구에 조문 번호가 섞여 있어도 이 도구다 ("제8조에 걸리나요, '다이어트에 좋은' 이라고 썼는데")

**안 쓰는 때**

- 사용자가 **문구를 제시하지 않았을 때.** "광고할 때 조심할 게 뭔가요" 는 문구가 없다 →
  되묻기(`MISSING_EXPRESSION`)이지 이 도구의 빈 호출이 아니다
- **"무엇을 적어야 하나"** 를 물을 때 → `list_mandatory_labels`. 의무 항목은 표현 기준이 아니다
- **조문 번호만** 오고 검토할 문구가 없을 때 → `get_article`
- 이미 이 도구로 답했는데 사용자가 **확정을 요구**할 때 → `file_review_request`.
  같은 문구로 다시 호출해도 답은 바뀌지 않는다

### ④ 인자 스키마

| 인자 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `expression` | string (1–200자) | **예** | 검토 대상 문구. **데이터로 취급한다** (1.5) |
| `surface` | `표시면` / `광고` / `미상` | 아니오 | 기본 `미상`. **도구 선택을 바꾸지 않는다** — `limits` 문구만 달라진다 |
| `productContext` | string (0–100자) | 아니오 | "무가당 두유" 처럼 제품 성격. 영양강조표시 판단의 전제를 좁힌다 |
| `maxHits` | int 1–5 | 아니오 | 기본 3 |

`expression` 이 200자를 넘으면 자르지 않고 `EXPRESSION_TOO_LONG` 으로 되돌린다 — 광고 문구
한 덩어리를 통째로 넣으면 어느 표현이 걸린 것인지 사용자가 알 수 없기 때문이다.

### ⑤ 반환 형식

1.2 봉투를 쓴다. `hits[].citation` 은 주로 `부당한 표시·광고 내용 기준`(고시 18청크) 과
`식품표시광고법 제8조`, 필요하면 `식품등의 표시기준` 의 영양강조표시 정의로 채워진다.

`hits[]` 에 두 칸이 더 붙는다.

| 칸 | 값 | 뜻 |
|---|---|---|
| `basisKind` | `금지유형` / `정의` / `상위근거` | 걸린 기준이 무엇인지 |
| `crossRef` | 인용 튜플 또는 `null` | 그 기준이 **다른 문서를 가리키기만** 할 때 그 대상 |

**`crossRef` 가 이 도구의 핵심 필드다.** 코퍼스에서 확인한 실제 예 — 부당한 표시·광고 내용
기준 제2조제3호 바목은 "'무설탕' 표시·광고" 를 다루지만, 기준 자체는
`식품등의 표시기준 별지1 제1호아목3)가) 영양강조 표시기준` 을 가리키기만 한다. 그 별지 본문은
청크가 아니라 별표 파일에 있고, 도구가 그것까지 붙이지 못하면 답은 "어디를 보라" 까지다.
그 사실을 숨기지 않고 `crossRef` 와 `coverage: partial` 로 내보낸다.

### ⑥ 실패 정의와 뒤 행동

| 코드 | 무엇이 일어난 것 | 뒤 행동 | 사용자에게 나가는 말 |
|---|---|---|---|
| `MISSING_EXPRESSION` | `expression` 이 비었다 | **되묻기** | "검토할 문구를 그대로 적어 주세요" |
| `EXPRESSION_TOO_LONG` | 200자 초과 | **되묻기** | "확인하려는 표현 한 구절만 남겨 주세요" |
| `NO_MATCH` | 걸리는 기준을 찾지 못했다 | **보류** | "이 자료에서는 걸리는 기준을 찾지 못했습니다. 문제없다는 뜻은 아닙니다" |
| `CROSS_REF_UNRESOLVED` | 기준이 별지·별표를 가리키는데 본문이 없다 | **보류** | 가리키는 곳을 그대로 알리고 거기까지만 답한다 |
| `AMBIGUOUS_EXPRESSION` | 서로 다른 기준 2개 이상이 같은 무게로 걸렸다 | **되묻기** | 어느 쪽을 뜻했는지 하나만 묻는다 |
| `OUT_OF_SCOPE` | 고정 목록 7건 중 하나에 걸렸다 | **보류** | 소관 법령을 고정 목록에서 꺼내 안내. 내용은 답하지 않는다 |
| `CORPUS_UNAVAILABLE` | 코퍼스를 읽지 못했다 | **재시도 1회** → 보류 | "자료를 불러오지 못했습니다" |
| `CORPUS_STALE` | `corpusAgeDays` 가 임계를 넘었다 | **보류** (답에 경고 동반) | 수집일을 밝히고 최신 확인을 권한다 |

`NO_MATCH` 가 **보류이지 "괜찮다" 가 아닌 이유** — 이 제품은 불필요한 보류가 근거 없는 확답보다
싸다고 정했다 (PRD 1절). 못 찾은 것을 "문제없음" 으로 옮기는 순간 그 저울이 뒤집힌다.

## 3. `list_mandatory_labels` — 식품유형별 의무 표시사항 조회

### ① 이름
`list_mandatory_labels` (의무 표시사항 조회) · **읽기**

### ② 하는 일 한 문장
사용자가 지정한 **식품유형에 붙는 의무 표시사항 목록**을 근거 조문과 함께 돌려준다.

### ③ 쓰는 때 · 안 쓰는 때

**쓰는 때**

- 사용자가 **식품유형(또는 제품 이름으로 유형을 특정할 수 있는 것)** 을 제시하고
  **"무엇을 적어야 하나"** 를 물을 때
- 만든 표시사항에서 **빠진 것**을 확인하려 할 때 (목록을 받아 사용자가 대조한다)

**안 쓰는 때**

- 사용자가 **특정 표현을 써도 되는지** 물을 때 → `search_expression_rule`.
  **그 표현이 표시면에 들어갈 말이어도 마찬가지다.** 이 도구는 "무엇을 적어야 하나" 만 답하고
  "이 말을 써도 되나" 는 답하지 않는다
- **식품유형이 없을 때** → 추측하지 않고 되묻기(`MISSING_FOOD_TYPE`). "우리 제품" 만으로는
  못 부른다
- 표시**방법**(글씨 크기·표시면 구분)만 물을 때 → 이 도구는 항목 목록이지 서식이 아니다.
  근거 조문이 규칙 별표 2·3 을 가리키므로 `crossRef` 로 넘긴다
- 조문 번호로 물을 때 → `get_article`. 표시기준 고시는 조문 번호 체계가 아니라
  `Ⅰ. 총 칙 …` 구조라서 조문 번호로는 이 도구를 부를 수 없다

### ④ 인자 스키마

| 인자 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `foodType` | enum (아래 10종 + `공통`) | **예** | 코퍼스에서 유형 이름이 붙어 검색되는 것만 열거했다 |
| `attributes` | string[] (`알레르기유발물질` / `유전자변형식품` / `조사처리` / `장기보존` / `인삼·홍삼`) | 아니오 | "해당 경우에 한함" 항목을 켜는 스위치 |
| `includeCommon` | boolean | 아니오 | 기본 `true`. 공통표시기준을 같이 받을지 |

**`foodType` enum (10종)** — 과자류ㆍ빵류 또는 떡류 / 빙과류 / 코코아가공품류 또는 초콜릿류 /
당류 / 잼류 / 두부류 또는 묵류 / 식용유지류 / 면류 / 음료류 / 특수영양식품.

표시기준 고시가 나누는 식품유형은 **27종**인데 enum 은 10종이다. 확인한 사실은 다음과 같다
(9절에 측정 방법을 적었다).

- 유형 이름이 표시사항 청크에 붙어 검색되는 것: **11종**
- 그중 **주류는 뺐다** — 코퍼스 `outOfScope` 에 "주류 표시(주세법 및 주류 관련 고시)" 가 있다.
  자료가 있어도 **범위 밖 판정이 앞선다** (7.4)
- 나머지 16종의 표시사항 청크 18개는 상위 유형 이름을 잃고 `2) 표시사항`·`거) 기타표시사항`
  으로 시작한다 → 유형으로 못 찾는다 → `TYPE_NOT_COVERED`

**없는 유형을 enum 에 넣지 않은 이유** — 넣으면 도구가 호출은 되고 빈 결과를 준다. 그러면
모델은 "그 유형은 의무 표시사항이 없다" 로 읽는다. 못 찾은 것과 없는 것을 구별하려면
**부를 수 없어야 한다.**

### ⑤ 반환 형식

1.2 봉투를 쓰되 `hits[]` 대신 `items[]` 를 쓴다.

```jsonc
{
  "ok": true, "code": "OK",
  "foodType": "음료류",
  "items": [
    { "label": "제품명",          "requiredWhen": "항상",                  "citation": { } },
    { "label": "영양성분",         "requiredWhen": "다류 중 침출차 등 제외",   "citation": { } },
    { "label": "알레르기 유발물질", "requiredWhen": "해당 경우에 한함",        "citation": { } }
  ],
  "commonRules": [ { "label": "주표시면·정보표시면 구분", "crossRef": { } } ],
  "coverage": { "level": "partial", "note": "표시방법·글씨크기는 규칙 별표 2·3 소관" },
  "limits": ["이 목록은 고시가 정한 항목이고, 개별 제품의 충족 여부는 판단하지 않았습니다"],
  "corpusAsOf": "2026-08-28", "corpusAgeDays": 3
}
```

`requiredWhen` 을 따로 두는 이유 — 고시가 항목 절반을 "해당 경우에 한함" 으로 단다.
그 꼬리표를 떼고 평평한 목록으로 주면 사용자는 전부 의무로 읽는다.

### ⑥ 실패 정의와 뒤 행동

| 코드 | 무엇이 일어난 것 | 뒤 행동 | 사용자에게 나가는 말 |
|---|---|---|---|
| `MISSING_FOOD_TYPE` | `foodType` 이 없다 | **되묻기** | "식품유형을 알려 주세요 (예: 음료류, 과자류)" |
| `TYPE_NOT_COVERED` | enum 밖 유형이다 (17종) | **보류** → 공통표시기준만 제시 후 **이관 제안** | "그 유형의 개별 표시사항은 이 자료에 없습니다. 공통 항목까지만 안내합니다" |
| `AMBIGUOUS_FOOD_TYPE` | 제품 설명이 두 유형에 걸린다 (예: 두유 → 음료류 / 두부류) | **되묻기** | 둘 중 하나를 고르게 한다 |
| `CROSS_REF_UNRESOLVED` | 별표 본문이 없다 (표시방법·서식) | **보류** | 가리키는 별표 이름까지만 답한다 |
| `OUT_OF_SCOPE` | 축산물·주류·건기식 기능성 등 고정 목록 | **보류** | 소관 법령 안내 |
| `CORPUS_UNAVAILABLE` | 코퍼스를 읽지 못했다 | **재시도 1회** → 보류 | "자료를 불러오지 못했습니다" |
| `CORPUS_STALE` | 수집일이 오래됐다 | **보류** (경고 동반) | 수집일 고지 |

**enum 밖 판정 순서** — `foodType` 이 enum 10종 밖이면 코퍼스 `outOfScope` 고정 목록
7건을 **먼저** 대조한다. 걸리면 `OUT_OF_SCOPE`, 안 걸리면 `TYPE_NOT_COVERED` 다.
이 순서가 없으면 탁주(자료는 있는데 범위 밖, 7.4)와 된장·장류(범위 안인데 자료 없음)가
같은 코드로 떨어져 구별되지 않는다. (2026-08-31, 패킷 5.5 자리 1 을 계약 본문으로)

## 4. `get_article` — 조문 원문 조회

### ① 이름
`get_article` (조문 원문 조회) · **읽기**

### ② 하는 일 한 문장
사용자가 **법령명과 조문 번호로 지목한 조문 하나**의 본문과 시행 상태를 돌려준다.

### ③ 쓰는 때 · 안 쓰는 때

**쓰는 때**

- 사용자가 **법령명 + 조문 번호**를 대고 그 조문이 무엇인지 물을 때
- 다른 도구의 반환에 실린 인용을 사용자가 **더 보자고** 할 때
- 조문 번호만 있고 **검토 대상 문구도, 식품유형도 없을 때**

**안 쓰는 때**

- **검토할 문구가 함께 왔을 때** → `search_expression_rule`. 문구 대조는 그 도구의 일이고,
  이 도구는 대조를 하지 않는다. 필요한 조문은 그쪽 반환의 인용으로 딸려 온다
- **법령명이 없을 때** → 되묻기. 코퍼스에 법령·고시가 9종 있고 "제2조"·"제5조" 는 그중
  여러 곳에 다 있다. 법령명 없는 조문 번호는 식별자가 아니다
- **"조문 전부 보여 줘"** 처럼 범위를 안 좁힐 때 → `SCOPE_TOO_BROAD` 로 되묻기.
  이 도구는 덤프 창구가 아니다
- 표시기준 고시의 표시사항을 물을 때 → `list_mandatory_labels`. 그 고시는 조문 번호 체계가 아니다

### ④ 인자 스키마

| 인자 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `lawName` | enum (아래 9종) | **예** | 코퍼스 `source` 값 |
| `article` | string (`제8조`, `제5조의2`) | **예** | 조 |
| `paragraph` | string (`제1항`) | 아니오 | 항. 사용자 표기(`①`)도 받아 정규화한다 |
| `item` | string (`제3호`) | 아니오 | 호 |

**`lawName` enum (9종)** — 식품표시광고법 / 식품표시광고법 시행령 / 식품표시광고법 시행규칙 /
부당한 표시·광고 내용 기준 / 식품등의 표시기준 / 어린이 기호식품 알레르기 표시기준 /
어린이 기호식품 영양성분·고카페인 표시기준 / 유전자변형식품등의 표시기준 /
표시·광고 심의 및 이의신청 기준.

`article` 없이 부를 수 없다. 인자가 다 비면 그건 조회가 아니라 덤프 요청이다.

### ⑤ 반환 형식

```jsonc
{
  "ok": true, "code": "OK",
  "citation": { "lawName": "...", "kind": "법률", "path": "제8조제1항제3호",
                "url": "...", "effectiveDate": "2025-09-19", "inForce": true },
  "text": "...",                                     // 지정한 조문 하나. 2000자 상한
  "pointsTo": null,                                  // "별표 2" 처럼 가리키기만 하면 그 이름
  "pendingAmendment": { "effective": "2026-11-27" }, // 없으면 null
  "limits": [], "corpusAsOf": "2026-08-28", "corpusAgeDays": 3
}
```

**한 번에 조문 하나.** 여러 조문을 요청하면 반환이 아니라 `SCOPE_TOO_BROAD` 다.
`text` 는 사용자가 범위를 지정한 그 조문이므로 1.3 이 금지한 "원문 덤프" 가 아니다 —
덤프는 **사용자가 지정하지 않은 범위**를 쏟는 것을 말한다.

`pendingAmendment` 는 코퍼스 `collection-report.json` 의 `pendingEffective`·`pendingAmendment`
에서 온다. 지금 코퍼스에 실제로 두 건 있다 (식품표시광고법 2026-11-27, 식품등의 표시기준
2028-01-01). 이 칸이 비어 있으면 사용자는 오늘 본 조문이 계속 유효하다고 믿는다.

### ⑥ 실패 정의와 뒤 행동

| 코드 | 무엇이 일어난 것 | 뒤 행동 | 사용자에게 나가는 말 |
|---|---|---|---|
| `MISSING_LAW_NAME` | 법령명이 없다 | **되묻기** | "어느 법령의 조문인가요" + enum 중 후보 제시 |
| `MISSING_ARTICLE` | 조 번호가 없다 | **되묻기** | "몇 조인지 알려 주세요" |
| `ARTICLE_NOT_FOUND` | 그 법령에 그 조문이 없다 | **보류** | 없다고 말한다. **가까운 조문으로 바꿔 답하지 않는다** |
| `SCOPE_TOO_BROAD` | 범위를 안 좁혔거나 여러 조문을 요구했다 | **되묻기** | 한 조문으로 좁혀 달라고 한다 |
| `POINTER_ONLY` | 조문이 "별표 N과 같다" 로 끝난다 | **보류** | 가리키는 별표 이름까지만 답한다 |
| `TABLE_NOT_COLLECTED` | 가리키는 별표 본문이 코퍼스에 없다 | **보류** → 반복되면 **이관** | 어느 별표가 없는지 밝힌다 |
| `NOT_IN_FORCE` | `inForce` 가 false 거나 시행 전이다 | **보류** (조문은 주되 상태를 앞에 붙인다) | 시행일을 먼저 말한다 |
| `OUT_OF_SCOPE` | 고정 목록 7건 | **보류** | 소관 법령 안내 |
| `CORPUS_UNAVAILABLE` | 코퍼스를 읽지 못했다 | **재시도 1회** → 보류 | "자료를 불러오지 못했습니다" |
| `CORPUS_STALE` | 수집일이 오래됐다 | **보류** (경고 동반) | 수집일 고지 |

`ARTICLE_NOT_FOUND` 에서 **가까운 조문으로 갈아타지 않는 이유** — 사용자가 조문 번호를 댈
때는 이미 어딘가에서 그 번호를 봤다는 뜻이다. 다른 조문을 대신 주면 사용자는 자기가 본
번호가 그것이라고 믿게 된다.

## 5. `file_review_request` — 검토 요청 접수 · **쓰기**

### ① 이름
`file_review_request` (검토 요청 접수) · **쓰기 · 사람 승인 필요**

### ② 하는 일 한 문장
읽기 도구로 답한 뒤에도 남은 **확정 판단 요구를 검토 담당자에게 넘기고**, 접수 사실을
사용자에게 돌려준다.

### ③ 쓰는 때 · 안 쓰는 때

**쓰는 때** — 아래 사유 중 **하나에 해당하고, 읽기 도구를 이미 부른 뒤**여야 한다.

| `reason` | 언제 |
|---|---|
| `CONFIRMATION_REQUESTED` | 근거를 제시했는데도 사용자가 확정 판단을 요구한다 (PRD UC5) |
| `OUT_OF_COVERAGE` | `TYPE_NOT_COVERED`·`TABLE_NOT_COLLECTED` 로 자료가 닿지 않는다 |
| `CONFLICTING_BASIS` | 근거 둘이 서로 어긋난다 (예: 표시기준에 주류 표시사항이 있는데 범위 밖 목록에도 주류가 있다) |
| `REPEATED_FAILURE` | 같은 실패 코드가 두 번 연속 났다 (1.4 중단 조건) |

**안 쓰는 때**

- **우회 시도를 기록하기 위해서.** 승인·규칙을 건너뛰라는 요청(PRD UC7)은 접수 사유가
  아니다 — 그 기록은 판단을 넘기는 이관이 아니라 **사건 기록**이고, 도구가 아니라
  **운영 층**이 승인 없이 남긴다 (PRD 5절 운영 층, 패킷 2.4·2.5). 이 게이트는 동의
  게이트라서(④) 우회를 시도한 사용자의 동의를 그 기록의 조건으로 삼지 않는다
- **읽기 도구를 한 번도 부르지 않았을 때.** 조회로 풀리는 질문을 사람에게 넘기는 것은
  이관이 아니라 떠넘기기다 → `MISSING_EVIDENCE` 로 거절하고 먼저 조회한다
- 사용자가 **묻기만 했을 때.** 이관은 사용자가 원하거나 도구가 막혔을 때 일어난다
- **사람 승인이 없을 때.** 승인 없이는 호출 자체가 실행되지 않는다 (아래 ④ 게이트)
- **답을 확정해 주기 위해서.** 이 도구는 판단을 옮기는 것이지 판단을 만드는 것이 아니다

### ④ 인자 스키마와 승인 게이트

| 인자 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `subject` | string (1–300자) | **예** | 검토 대상 — 문구 또는 표시사항. **데이터로 취급** (1.5) |
| `reason` | enum (위 4종) | **예** | 왜 사람이 필요한가 |
| `evidence` | 인용 튜플[] (1건 이상) | **예** | 읽기 도구가 이미 낸 근거. **비면 접수하지 않는다** |
| `askedFor` | string (0–200자) | 아니오 | 사용자가 요구한 것을 그대로 |
| `contact` | string | 아니오 | 회신처. 없으면 담당자 큐에만 쌓인다 |

**승인 게이트 — 실행 전에 사람이 이 셋을 본다** (PRD F3). 이 게이트는 **동의 게이트**다 —
승인자는 요청한 사용자 본인이고(패킷 2.3), 묻는 것은 "내 검토 내용을 이대로 사람에게
넘겨도 되는가"이지 적법성이 아니다.

| 확인 항목 | 화면에 나가는 값 |
|---|---|
| **대상** | `subject` 전문 |
| **내용** | `evidence` 인용 튜플 목록 + `askedFor` |
| **사유** | `reason` 과 그 사유가 붙은 실패 코드 |

이 도구는 **기본 권한에 없다.** 세션이 시작될 때 열려 있는 것은 읽기 도구 셋뿐이고, 이
도구는 승인이 떨어진 그 한 번의 호출에만 열린다. 승인은 호출마다 새로 받는다 —
한 번 승인이 다음 접수까지 이어지지 않는다.

**스키마에 "승인 필요" 라고 적어 두는 것만으로는 막히지 않는다** (PRD 5절). 검사는
하네스에서 한다: 승인 토큰 없는 호출은 도구에 닿기 전에 거부된다.

### ⑤ 반환 형식

```jsonc
{
  "ok": true, "code": "OK",
  "ticketRef": "REQ-2026-0831-014",   // 사람이 부를 수 있는 번호
  "status": "pending_human",
  "echo": { "subject": "...", "reason": "CONFIRMATION_REQUESTED", "evidenceCount": 2 },
  "limits": ["접수만 되었습니다. 검토 결과가 아닙니다"]
}
```

**접수 번호 접두사는 `REQ-` 다** — m05 코퍼스의 별표 종류 접두사 `REV` 와 뜻이 겹치지
않게 (PLAN D8, 2026-08-31 결정). 코퍼스는 읽기 전용이라 이쪽을 바꿨다.

**`echo` 를 돌려주는 이유** — 사용자가 승인 화면에서 본 것과 실제로 접수된 것이 같은지
사용자 쪽에서 확인할 수 있어야 한다. `evidence` 본문은 되돌려주지 않고 건수만 준다 (1.3).

접수는 **큐에 넣는 것까지**다. 메일·티켓 시스템에 붙이지 않는다 (PRD 7절).

### ⑥ 실패 정의와 뒤 행동

| 코드 | 무엇이 일어난 것 | 뒤 행동 | 사용자에게 나가는 말 |
|---|---|---|---|
| `APPROVAL_REQUIRED` | 승인 토큰 없이 호출됐다 | **보류** | 승인 화면을 띄운다. 도구는 실행되지 않았다 |
| `APPROVAL_DENIED` | 사람이 승인하지 않았다 | **보류** | "접수하지 않았습니다" 를 **명시한다.** 조용히 넘어가지 않는다 |
| `APPROVAL_TIMEOUT` | 승인 대기가 만료됐다 | **보류** | 다시 요청하려면 어떻게 하는지 안내 |
| `MISSING_SUBJECT` | 검토 대상이 비었다 | **되묻기** | "무엇을 검토받고 싶은지 적어 주세요" |
| `MISSING_EVIDENCE` | `evidence` 가 비었다 | **보류** → 자기 교정 (사용자에게 묻지 않는다) | 먼저 읽기 도구를 부른 뒤 다시 접수한다 |
| `DUPLICATE_REQUEST` | 같은 `subject` + `reason` 이 이미 대기 중이다 | **보류** | 기존 `ticketRef` 를 알린다. 두 번 접수하지 않는다 |
| `SINK_UNAVAILABLE` | 큐에 넣지 못했다 | **재시도 1회** → 보류 | "접수하지 못했습니다" 를 명시한다 |

**우회 요청(PRD UC7)은 이 도구의 실패 코드에도 `reason` 에도 없다.** 우회 요청은 거절하되
기록은 남긴다 — 기록이 다음 계약 수정의 근거가 되기 때문이다 (PRD 5절 운영 층). 다만 그
기록은 판단을 넘기는 이관이 아니라 **사건 기록**이므로 이 도구를 거치지 않고, **운영 층이
승인 없이** 남긴다 (패킷 2.4·2.5). 사용자에게는 **요청을 들어주지 않았다**고 말하고,
확답이 필요하면 정당한 경로 — `CONFIRMATION_REQUESTED` 접수 — 를 제안한다.

## 6. 도구쌍 6개 '쓰는 때' 대조 (완료 기준 b)

네 도구에서 나오는 쌍은 6개다. 각 쌍에 **겹치지 않게 하는 한 문장**을 붙였다.

| # | 쌍 | 가르는 것 | 겹치지 않는 이유 |
|---|---|---|---|
| 1 | `search_expression_rule` ↔ `list_mandatory_labels` | 표현이 왔는가, 유형이 왔는가 | 전자는 "이 말을 써도 되나", 후자는 "무엇을 적어야 하나". **표현이 오면 그것이 표시면에 들어갈 말이어도 전자다** |
| 2 | `search_expression_rule` ↔ `get_article` | 검토할 문구가 함께 왔는가 | 문구가 있으면 대조가 필요하다 → 전자. 조문 번호만 있으면 본문만 필요하다 → 후자 |
| 3 | `search_expression_rule` ↔ `file_review_request` | 조회인가, 조회 뒤인가 | 후자는 **전자를 이미 부른 뒤에만** 부를 수 있다 (`MISSING_EVIDENCE`) |
| 4 | `list_mandatory_labels` ↔ `get_article` | 유형이 왔는가, 조문 번호가 왔는가 | 표시기준 고시는 조문 번호 체계가 없어 후자로 부를 수 없고, 조문 번호에는 식품유형이 없어 전자로 부를 수 없다 |
| 5 | `list_mandatory_labels` ↔ `file_review_request` | 조회인가, 조회 뒤인가 | 3번과 같다. `TYPE_NOT_COVERED` 는 **먼저 전자를 불러야 나오는 코드**다 |
| 6 | `get_article` ↔ `file_review_request` | 조회인가, 조회 뒤인가 | 3번과 같다. `TABLE_NOT_COLLECTED` 역시 조회 뒤에만 난다 |

**세 읽기 도구는 서로 배타적이고, 쓰기 도구는 읽기 도구 뒤에만 온다.** 그래서 쌍 3·5·6 은
같은 문장으로 닫힌다 — 쓰기 도구의 "쓰는 때" 에는 **시점 조건**이 들어 있고, 읽기 도구의
"쓰는 때" 에는 없다.

**복합 질문은 도구를 합치지 않고 순서로 푼다.** "우리 음료에 뭘 적어야 하고 '무설탕' 도 써도
되나요" 는 `list_mandatory_labels(음료류)` → `search_expression_rule("무설탕")` 두 번이다.
한 도구가 둘을 다 하면 실패했을 때 무엇이 실패한 것인지 말할 수 없다 (PRD 1절).

## 7. 겹치는 자리를 실제로 닫은 문장 (완료 기준 c)

경계에 진짜로 겹치는 자리가 있다. PLAN 이 슬라이스 1을 `[어려움]` 으로 표시한 이유다.

### 7.1 "'무설탕' 이라고 **표시**해도 되나요"

주제로는 셋에 걸린다 — ① 광고 표현 기준(부당 표시·광고), ② 영양강조표시 정의(표시기준),
③ 표시면에 들어가니 의무 표시사항.

**닫은 문장** — `list_mandatory_labels` 의 안 쓰는 때:

> 사용자가 특정 표현을 써도 되는지 물을 때는 쓰지 않는다. **그 표현이 표시면에 들어갈
> 말이어도 마찬가지다.** 이 도구는 "무엇을 적어야 하나" 만 답한다.

그래서 `search_expression_rule("무설탕", surface="표시면")` 하나다. `surface` 인자는
**도구 선택을 바꾸지 않고** `limits` 문구만 바꾼다 — 이 인자가 선택에 개입하면 방금 닫은
경계가 다시 열린다.

이 사례는 코퍼스로 검증된다. 부당한 표시·광고 내용 기준 제2조제3호 바목이 "'무설탕'
표시·광고" 를 직접 다루고, 표시기준 별지1 영양강조 표시기준을 `crossRef` 로 가리킨다.
답은 "부당 표시·광고 기준에 걸리는 표현이고, 기준값은 별지1을 봐야 한다" 까지다.

### 7.2 "제8조 제1항 제3호에 걸리는 광고인가요, '다이어트에 좋은' 이라고 썼는데"

조문 번호와 문구가 같이 왔다.

**닫은 문장** — `get_article` 의 안 쓰는 때:

> 검토할 문구가 함께 왔을 때는 쓰지 않는다. 문구 대조는 `search_expression_rule` 의 일이고,
> 이 도구는 대조를 하지 않는다.

`search_expression_rule` 하나를 부르고, 사용자가 조문 본문을 더 보자고 하면 그때
`get_article` 을 부른다.

### 7.3 커버리지 밖 유형을 물었을 때

`TYPE_NOT_COVERED` 가 나면 곧장 이관하고 싶어진다.

**닫은 문장** — `file_review_request` 의 안 쓰는 때:

> 읽기 도구를 한 번도 부르지 않았을 때는 쓰지 않는다.

`TYPE_NOT_COVERED` 는 **읽기 도구를 부른 결과로만 나오는 코드**이므로 순서가 강제된다.
공통표시기준까지 답하고, 그래도 남으면 `reason: OUT_OF_COVERAGE` 로 이관을 제안한다.

### 7.4 주류 — 자료는 있는데 범위 밖인 것

식품등의 표시기준은 주류 표시사항을 담고 있다(LBL 청크에 탁주·맥주·증류주 기타표시사항이
있다). 그런데 코퍼스 `outOfScope` 에 "주류 표시(주세법 및 주류 관련 고시)" 가 있다.

**닫은 결정** — `foodType` enum 에서 주류를 뺐다. **범위 밖 판정이 자료 유무보다 앞선다.**
사용자가 주류를 물으면 `OUT_OF_SCOPE` 로 소관을 안내하고, 그래도 답이 필요하면
`reason: CONFLICTING_BASIS` 로 이관한다. 이 저울은 PRD 1절이 정했다 — 불필요한 보류가
근거 없는 확답보다 싸다.

## 9. 코퍼스에서 확인한 것 (인자·반환 필드의 근거)

이 정의서의 enum 과 실패 코드는 추측이 아니라 코퍼스를 읽어서 나왔다. 확인일 2026-08-31.

| 확인한 것 | 값 | 어디에 쓰였나 |
|---|---|---|
| 청크 수 / 필드 | 365개 / `id·source·sourceKind·lawName·path·text·url·effectiveDate·inForce` | 1.1 인용 튜플 |
| 법령·고시 종류 | 9종 | `get_article.lawName` enum |
| `outOfScope` | 7건 (수출 라벨·화장품·의약품·건기식 기능성·축산물·주류·협찬) | 세 읽기 도구의 `OUT_OF_SCOPE` |
| 표시기준이 나누는 식품유형 | **27종** | `list_mandatory_labels` 배경 |
| 유형 이름이 표시사항 청크에 붙어 검색되는 유형 | **11종** | enum 후보 |
| enum 에 넣은 것 | **10종** (11종에서 주류 제외) | `foodType` enum |
| 유형 이름을 잃은 표시사항 청크 | **18개** (`2) 표시사항`·`거) 기타표시사항` 으로 시작) | `TYPE_NOT_COVERED` 가 필요한 이유 |
| 별표가 비어 있는 고시 | `ALG` 0건, `GMO` 0건 | `TABLE_NOT_COLLECTED` |
| 시행 예정 개정 | 식품표시광고법 2026-11-27, 식품등의 표시기준 2028-01-01 | `pendingAmendment`, `NOT_IN_FORCE` |
| 코퍼스 수집일 | 2026-08-28 (`includesFutureEffective: false`) | `corpusAsOf`, `CORPUS_STALE` |
| '무설탕' 을 다루는 조문 | 부당한 표시·광고 내용 기준 제2조제3호 바목 → 표시기준 별지1 을 가리킴 | 7.1 `crossRef` |

**측정 방법** — `m05-rag-chatbot-service/app/public/corpus/chunks.json` 과
`collection-report.json` 을 Node 로 읽어 셌다. 식품유형 27종 목록은
`식품등의 표시기준 Ⅰ. 총 칙 2. 구 성` 청크에서 가져왔고, "유형 이름이 붙어 검색되는가" 는
표시사항 청크의 앞 120자에 그 유형 이름이 있는지로 판정했다. 코퍼스는 **읽기만 했다.**

### 발견 — PRD UC2 의 예시

PRD 3절 UC2 가 "과자류인데 표시사항 뭐가 필요한가요" 를 예로 든다. 과자류는 enum 안에 있어
그대로 동작한다. 다만 **PRD 가 든 예시가 27종 중 어디에 속하는지에 따라 결과가 갈린다** —
장류·조미식품·유가공품처럼 자주 물어볼 유형이 `TYPE_NOT_COVERED` 로 떨어진다.
슬라이스 3 의 테스트 문항에 이 경우를 넣는 것이 맞다 (PLAN 슬라이스 3 완료 기준 "도구 오류 ≥1").

# m04. 도구 설계 — 식품 표시·광고 사전검토 안내 에이전트

> 배포 주소: 없음 — 이 과제의 산출물은 **설계 문서**이지 배포 앱이 아니다.

## 과제 개요

서비스 가이드 챗봇의 **경계**를 설계한다. 어떤 서비스를 맡기고 **어디에서 멈추게 할지**를
계약·권한·관찰·중단의 한 묶음(설계 패킷)으로 정리한다.

- **도메인: 식품 표시·광고 규정** — [m05](../m05-rag-chatbot-service/)와 같은 도메인.
  m05가 "조문을 찾아 보여 주는 챗봇"이었다면, m04는 그 검색을 **도구 하나로 두고**
  표시사항 점검·문구 대조·사람 검토 이관까지 묶은 **에이전트의 경계**를 설계한다.
- LMS: https://learn.modulabs.co.kr/camp/136/courses/2171/node-version/5160/steps/26040
- 요구사항: [PRD.md](PRD.md)

### 제출 루브릭 (정본 — 범위를 이것이 정한다)

| 학습목표 | 평가기준 |
|---|---|
| 다양한 상황에 대비한 서비스 설계를 할 수 있다 | 테스트 문항에 **공격 시도(규칙 우회 요청) 1개**와 **각 문항의 기대 동작**을 기록했는가 |
| 적절한 프로젝트 설계를 할 수 있다 | **과거 생성한 서비스에서** 유의미한 챗봇 가이드 서비스를 설계한다 |
| 도구 정의서를 직접 설계할 수 있다 | 각 도구의 정의서에서 **'쓰는 때·안 쓰는 때'와 '실패 뒤 행동'** 을 모두 썼는가 |

> **루브릭에 실행이 없다.** 모델 실측, 계약 수정 전후 회귀, MCP 연결은 채점 대상이 아니다.
> 7강이 `traces/` 를 확인 지점으로 표시하지만, 같은 강의가 *"트레이스에는 실제 결과가 아니라
> 설계상 남겨야 할 관찰 항목을 채워"* 라고 쓴다. 그래서 트레이스는 **설계상 기대 기록**으로
> 채우고, 실측하지 않은 사실은 아래 "실행하지 않은 것과 이유"에 적는다.

## 설계 결정 요약

### 도구를 네 개만 둔 이유

도구를 나눈 기준은 **기능 분할이 아니라 실패 구별**이다. 이 도메인은 겉보기 문장이 거의 같은데
필요한 자료가 다르다 — "'무설탕' 써도 되나요"(표현 기준), "뭘 적어야 하나요"(의무 표시사항),
"제8조 제1항 제3호가 뭔가요"(조문 원문). 넷을 한 도구로 뭉치면 모델은 **무엇을 못 찾았는지**
말할 수 없고, 다섯 개로 늘리면 선택 실패가 늘어난다(안티패턴: 도구 남발). 그래서 읽기 셋 +
쓰기 하나에서 멈췄고, 경계는 주제가 아니라 **"사용자가 무엇을 제시했는가"**로 갈랐다
(정의서 0절). 범위 밖은 다섯 번째 도구가 아니라 세 읽기 도구가 공통으로 내는 `OUT_OF_SCOPE`
— 범위 밖은 별도 자료가 아니라 **조회 실패의 한 종류**이기 때문이다.

### 권한을 나눈 기준

가른 기준은 기능이 아니라 **되돌릴 수 있는가**다. 읽기 셋은 몇 번을 불러도 밖에 남는 것이
없어 실패해도 답이 늦어질 뿐이지만, 검토 요청 접수는 사람의 큐에 항목을 만들고 그 항목을
사람이 읽는다 — 되돌리려면 사람이 개입해야 한다. 그래서 `file_review_request` 하나만
**기본 권한에서 닫고**(정의가 목록에 보이는 것은 모델이 "이관이라는 경로가 있다"를 알고
제안하기 위해서다) 호출마다 승인 토큰을 받게 했다. 승인이 상태가 되면 게이트가 아니라
설정이 되므로 "이 세션에서는 계속 허용"을 두지 않았고, 검사는 스키마가 아니라 **하네스**가
한다 — PRD 5절이 못 박은 대로 스키마는 안내이지 권한이 아니다(패킷 2.4).

### 실패 뒤 행동을 그렇게 정한 근거

행동 어휘를 **재시도 / 되묻기 / 보류 / 이관 넷**으로 묶고 오류 코드 25개 전부에 1차 행동을
하나씩 못 박았다(패킷 3.2, 미지정 0). 어휘가 늘면 "적절히 대응" 같은 판정 불가능한 칸이
생기기 때문이다. 배분이 **보류 14 · 되묻기 9 · 재시도 2**로 기운 것은 PRD 1절이 정한 저울
때문이다 — 틀린 답의 대가가 과징금·영업정지·회수라서 **불필요한 보류가 근거 없는 확답보다
싸다.** 그래서 `NO_MATCH` 는 "괜찮다"가 아니라 보류이고, 한 칸 차이로 보류가 허가로 바뀌는
자리를 4.4 가 문장까지 지정한다. **1차 행동이 `이관`인 코드는 0개**인데, 이것은 빠뜨린 것이
아니라 설계다 — 조회로 풀릴 것을 사람에게 넘기면 이관이 아니라 떠넘기기이므로, 이관은
누적 조건이나 사용자 발화에서만 켜진다(패킷 3.3).

## 실행하지 않은 것과 이유

**채점 범위 밖이라 뺀 것** (못 해서 뺀 것이 아니다):

- 모델을 실제로 돌린 트레이스 실측 — 루브릭에 실행 항목이 없다
- 계약 수정 전후 비교·회귀 측정 (8강) — 채점 대상이 아니다
- MCP 서버 연결 (5강 후반부) — 연결 방식이지 설계 점수에 붙지 않는다
- 서비스 UI·배포

**다음에 측정할 지점** — 실행 단계로 넘어간다면 이 순서로 잰다. 전부 **이 설계가 이미
판정 기준을 글자로 정해 둔 것**이라 재는 즉시 합불이 갈린다.

| # | 재는 것 | 어떻게 | 왜 이것부터 |
|---|---|---|---|
| 1 | **도구 선택 정확도** | 문항 8개(패킷 5.2)의 호출 지점 10개를 실제 모델에 흘려 기대 도구와 대조 | 이 설계의 핵심 주장이 "경계를 제시물로 가르면 안 겹친다"다. 겹치면 여기서 먼저 깨진다 |
| 2 | **Q2 ② 함정 통과율** | "표시면에 '무설탕'"을 `list_mandatory_labels` 로 받는 오답률 | 정의서 7.1 이 닫은 유일한 진짜 겹침이다. 문서로 닫은 것이 실제로 닫히는지 |
| 3 | **Q7 공격 거절률** | 우회 요청 + 문구 내 명령문에서 "괜찮다/문제없다" 문장이 나오는 비율 | 4.3 금지 문장이 모델 층에서 지켜지는지. 0%가 아니면 하네스 규칙으로 내려야 한다 |
| 4 | **최종 답 3번 칸 누락률** | "말할 수 없는 것"이 빠진 답의 비율 | 4.2 가 "비면 내보내지 않는다"고 정한 칸이다. 보류가 허가로 읽히는 자리가 여기 하나다 |
| 5 | **승인 게이트 우회 0건** | 토큰 없는 `file_review_request` 호출이 도구에 닿는지 | 하네스가 마지막 경계다(2.4). 여기서 1건이라도 새면 권한 분리가 이름만 남는다 |
| 6 | **`TYPE_NOT_COVERED` 실제 발생률** | 사용자 질문 표본에서 `foodType` enum 10종 밖 비율 | 아래 "미해결" 1번의 크기를 재는 값이다. enum 을 넓힐지 말지가 이 수치로 갈린다 |

## 미해결로 남긴 것 (사용자가 이대로 두기로 함)

슬라이스 1~4가 찾아낸 자리들에 대해 **2026-08-31 사용자 결정**이 내려왔다. 여섯 자리 중
**넷(2·3·4·5)은 슬라이스 6이 계약에 반영해 이 표에서 내렸다**:

- **접수 번호를 `REQ-` 로** 바꿨다 — m05 코퍼스 별표 종류 `REV` 와 겹치지 않게 (정의서 5절 ⑤)

  기록을 `file_review_request` 의 `reason` 에서 빼서 **운영 층이 승인 없이** 남기게 했다 —
  게이트에 예외를 뚫지 않고 모순이 사라진다 (패킷 2.3~2.5·5.5, 문항 Q7 은 도구 호출 0회로)

- **enum 밖 판정 순서를 계약 본문에** 올렸다 — `outOfScope` 먼저, 걸리면 `OUT_OF_SCOPE`,

## 1. 문제 정의

**이 챗봇이 어떤 질문에, 어떤 근거로 답해 주는가**

Claude Code 설정·확장 기능(CLAUDE.md, settings.json, hooks, MCP, skills, subagents,
slash commands)에 대한 "이거 어떻게 설정해요?" 류의 질문에, **공식 문서 원문과 그 URL을
근거로** 답한다.

**왜 RAG여야 하는가** — 이 도메인은 일반 LLM이 특히 잘 틀린다:

| 실패 양상 | 예 | 이 챗봇의 대응 |
|---|---|---|
| 없는 설정 키를 지어냄 | 그럴듯한 이름의 `settings.json` 키를 만들어 낸다 | 출처 칩 → 원문 확인 (3절 F3) |
| 옛 스펙을 현재로 말함 | 도구가 빠르게 바뀌어 학습 시점의 스펙이 이미 다르다 | **수집 시점을 화면에 표기** (3절 F8, 4·5절) |
| 파일 위치를 혼동 | 프로젝트 `.claude/` vs `~/.claude/` vs 로컬 오버라이드 | 섹션 정보를 보존한 청크 (4절) |
| 비슷한 기능을 뒤섞음 | hooks / skills / subagents / MCP 의 경계 | 근거 청크 밖으로 나가면 판정에 걸린다 (3절 F5) |

> "옛 스펙" 문제는 이 챗봇도 똑같이 겪는다. 일반 LLM은 학습 시점에, 이 챗봇은 **수집
> 시점**에 고정된다. 그 시점이 사용자에게 보이지 않으면 차이가 없다 — 그래서 수집 시점
> 표기가 장식이 아니라 기능이다.

**그래서 이 챗봇의 성공은 "답이 자연스러운가"가 아니라 "그 문장이 실제 문서 어느 줄에서
왔는지 사용자가 클릭해서 확인할 수 있는가"로 정의한다.** 이 챗봇이 다루는 범위(코퍼스)에
없으면 지어내지 않고, **범위 밖임을 말하는 것**이 정답이다.

> **"공식 문서에 없다"가 아니라 "이 챗봇의 범위에 없다"** 다. 코퍼스는 공식 문서 191페이지의
> 부분집합이므로(4절), 코퍼스 밖 질문에 "문서에 없습니다"라고 답하면 정당한 거절이 아니라
> **틀린 답**이다. 이 구분이 이 제품에서 가장 틀리기 쉬운 지점이다.

## 2. 타겟 유저

**주 사용자** — Claude Code를 쓰기 시작했고, 설정을 바꾸려는데 *어느 파일의 어느 키*인지
모르는 개발자. 공식 문서가 191페이지라 어디를 봐야 할지부터 막힌다.

**이 사용자의 특징이 설계에 미치는 영향:**

- 질문은 **한국어**로 한다 → 코퍼스도 한국어 우선 (4절)
- 답을 그대로 믿지 않고 **원문을 확인하려 한다** → 출처 링크가 장식이 아니라 핵심 기능
- 틀린 설정을 넣으면 도구가 조용히 동작을 안 하므로, **모르면 모른다고 하는 편이 낫다**
  → 불필요한 거절보다 **근거 없는 확답이 더 큰 손해**

**비사용자** — Claude Code를 처음 듣는 사람(개념 소개는 공식 문서가 이미 잘 한다),
Anthropic API 일반 사용자(도메인 밖).

## 3. 핵심 기능 (MVP)

반드시 있어야 하는 최소 기능. 이 목록에 없는 것은 MVP가 아니다.

| # | 기능 | 사용자가 확인할 수 있는 것 |
|---|---|---|
| F1 | 질문 입력 → 답변 스트리밍 | 답이 토큰 단위로 나오고, **취소 버튼**으로 중단된다 |
| F2 | 근거 검색 | 답변에 쓰인 청크가 몇 개, 어떤 경로로 뽑혔는지 보인다 |
| F3 | 출처 공개 | 답변 아래 **출처 칩** → 누르면 원문 조각과 **문서 URL**이 열린다 |
| F4 | **근거 상태 3단** | 아래 표대로 화면이 달라진다 |
| F5 | 자동 판정 | **규칙 배지 + LLM 배지** 두 층으로 붙는다 |
| F6 | 사람 피드백 | 좋아요/싫어요를 남기고, **자동 판정 결과와 나란히** 볼 수 있다 |
| F7 | **엔진 선택** | API / 로컬 Ollama 를 화면에서 고르고, 현재 엔진과 연결 상태가 항상 보인다 |
| F8 | **수집 시점 표기** | 이 답변이 어느 시점 문서에 근거하는지 화면에서 확인된다 |

**F4·F5를 MVP에 넣는 이유** — 이 둘이 빠지면 "그럴듯한 답"과 "근거 있는 답"이 화면에서
구분되지 않는다. 그건 이 제품의 존재 이유 자체가 사라지는 것이다.

### F4 — 근거 상태 3단

| 상태 | 화면 | 판정값 |
|---|---|---|
| 근거 충분 | 답변 + 출처 칩 | 정상 |
| 근거 약함 | 답변 + **한계 문장** + ⚠ 경고 배지 + 출처 칩 | `weak` |
| 범위 밖 | 답변 없음 + **다루는 범위 안내** | `refusal` (정당) |

상태를 가르는 신호는 **검색 최고 점수의 두 임계값**, 그리고 규칙 하나 —
**답변이 인용 ID를 하나도 달지 않으면 "근거 충분"으로 표시하지 않는다.** 점수는 높은데
모델이 청크를 안 쓰는 경우가 흔하고, 임계값만으로는 못 잡는다.

> 임계값 수치는 여기 쓰지 않는다 — PLAN·구현 영역.

### F5 — 판정은 규칙과 LLM 두 층

| 판정 항목 | 방식 | 근거 |
|---|---|---|
| 인용 여부 | **규칙** — 답변의 `[CC-nnn]`이 실제 검색된 청크 집합에 있는가 | 결정적·무료. 2b 모델보다 신뢰도가 높다 |
| 거절 여부 | **규칙** — 답변을 생성하지 않고 범위 안내로 종료했는가 | 상태로 판정 가능 |
| 근거성 | **LLM** — 답변 문장이 제공된 청크에서 나왔는가 | 규칙으로 못 잰다 |

- 명세가 "자동 판정(LLM-as-a-Judge, **기타 평가지표 등**)"이라고 써서 비-LLM 결정적 지표를
  허용한다. 규칙으로 잴 수 있는 것을 확률적 모델에 맡기지 않는다.
- **LLM 판정은 "현재 선택된 엔진"으로 돌린다.** 엔진마다 판정이 달라지는 것은 결함이 아니라
  확장 항목이 요구하는 **관측 대상**이다. 판정 엔진을 따로 고정하면 그 비교가 사라진다.
- **규칙 배지와 LLM 배지를 같은 모양으로 그리지 않는다** — 하나는 결정적, 하나는 확률적이라
  신뢰 수준이 다르다 (5절 화면 규칙 4).

### 생성 엔진 — 둘 다 MVP

| | MVP | 확장 |
|---|---|---|
| 무엇 | **API + 로컬 Ollama 둘 다.** 화면에서 전환 | 둘을 **나란히 두고 답변 리듬·판정 결과를 비교** |
| 기본값 | **API** — 링크로 처음 들어온 사람이 아무것도 고르지 않아도 동작해야 한다 | — |

명세는 "로컬 Ollama(`qwen3.5:2b` 등) **또는 API를** 활용해"라고 써서 **API를 1급 선택지로
허용**한다. 확장 점수가 붙는 것은 API를 쓰는 것이 아니라 **둘을 나란히 두고 비교하는 것**이다
("로컬 Ollama **외에** … 나란히 두고 … 어떻게 달라지는지 비교").

Ollama 단독 배포도 명세가 허용한다("실행 안내와 `OLLAMA_ORIGINS` … README에 정리"). 둘 다
두는 이유는 **채점자 편의와 확장 항목을 동시에 잡기 위해서**다.

**자동 폴백을 넣지 않는다.** Ollama 실패 시 조용히 API로 넘어가면 사용자가 어느 엔진의 답을
보는지 알 수 없고, 확장 항목의 비교가 오염된다. 실패는 실패로 표시한다.

> `[결정 필요]` **D5** — API 엔진 종류와 키 입력 방식. MVP로 올라왔으므로 **PLAN 작성 시**
> 정한다. 정적 배포에 키를 넣을 수 없으니 사용자가 화면에서 입력하는 방식이 유력하다.
> 그 경우 "링크만으로 바로"가 완전히 성립하지 않는다 → 8절 A1 각주 참조.

### 범위 — 191페이지 전부가 아니다

**"설정과 확장"** 한 주제로 좁힌다. 이 사용자가 실제로 막히는 곳이고, 오답을 판별하기 쉬워
루브릭이 성립한다.

수집 대상 후보:
`memory`(CLAUDE.md) · `settings` · `hooks` · `mcp` · `skills` · `sub-agents` ·
`slash-commands` · `claude-directory` · `features-overview`(언제 무엇을 쓰나)

> **코퍼스는 공식 문서의 부분집합이다.** 이 사실이 제품 문구를 규정한다 — 코퍼스 밖 질문에
> "공식 문서에 없습니다"라고 답하면 **틀린 답**이다. 예: Claude Code 요금제는 공식 문서에
> 있지만 이 코퍼스에는 없다. 범위 밖 안내는 **"이 챗봇의 범위 밖이며, 공식 문서의 다른
> 페이지에 있을 수 있다"** 까지 말해 주는 편이 정확하고 더 쓸모 있다 (7절).

> `[결정 필요]` **D2** 최종 페이지 목록과 청크 수. 자료 수집 슬라이스에서 원문을 읽고
> 확정한다. 명세는 청크 수를 강제하지 않는다. **후보 9페이지의 제목 수가 270개**로 측정돼
> 범위를 더 좁혀야 한다는 근거가 있다 ([FINDINGS](FINDINGS.md) 3절).

### 코퍼스 언어 — 확정

**한국어 우선. `docs/ko/<slug>.md` 가 404인 페이지만 영문으로 보충한다.** 청크에 언어를
기록한다.

- 코퍼스가 한 벌이라 벡터스토어를 두 번 만들 이유가 없다
- 확인된 구멍(`slash-commands`)이 생기지 않는다
- 언어를 실험 축에서 빼고 여기서 확정한다 — 벡터스토어를 두 벌 만드는 비용이 맞지 않는다 (9절)

### 청크 규칙

- **한 청크에 하나의 중심 사실.** 단독으로 읽어도 주어와 맥락이 서야 한다
- 보존할 것: **식별자 · 본문 · 출처 URL · 섹션 · 수집 시점 · 언어**
  — **본문만 남기지 않는다.** 저장 구조는 구현 결정이므로 여기 쓰지 않는다
- ID 규칙: `CC-001` 부터 (`CC` = Claude Code)
- 원문에 없는 연결을 요약으로 덧붙이지 않는다 — 출처가 있어도 환각을 감추는 재료가 된다

## 5. 화면 구성

**단일 페이지.** 별도 라우팅 없이 한 화면에서 질문 → 근거 → 답변 → 판정이 모두 관찰된다.

```
┌───────────────────────────────────────────────┐
│ 헤더 — 이 챗봇이 무엇을 근거로 답하는지        │
│   [엔진: API ▾ / Ollama]  ● 연결됨            │
│   📅 YYYY-MM-DD 기준 문서                      │
├───────────────────────────────────────────────┤
│ 준비 상태 (첫 방문 다운로드가 있을 때만)        │
│   임베딩 모델 로딩 진행률 · 캐시 여부           │
├───────────────────────────────────────────────┤
│ 대화 영역                                      │
│   ⓘ 각 질문은 독립적으로 처리됩니다             │
│                                                │
│   [질문]                                       │
│   [검색 단계]  n개 청크 검색됨 · 방식           │
│   [답변]       스트리밍 · 취소 버튼             │
│   [⚠ 근거 약함] 있을 때만 + 한계 문장           │
│   [출처 칩] CC-003  CC-007  → 클릭 시          │
│              근거 모달(원문 조각 + URL + 시점)  │
│                                                │
│   ┌ 규칙 판정 ─────────┐  결정적               │
│   │ 인용 ✓  거절 ✗     │                      │
│   └────────────────────┘                      │
│   ┌ LLM 판정 (API) ────┐  확률적               │
│   │ 근거성 ✓  95/100   │                      │
│   └────────────────────┘                      │
│   [피드백]  👍 👎                              │
├───────────────────────────────────────────────┤
│ 입력창                                         │
└───────────────────────────────────────────────┘
```

**화면이 지켜야 할 규칙:**

1. **답변과 판정은 서로 다른 시각적 층에 둔다.** 생성 문장이 자연스럽다는 사실과 출처를
   가진 답이라는 사실은 다르므로, 한 덩어리로 보이면 안 된다
2. **출처 칩은 답변 뒤에 붙는 장식이 아니라 클릭 가능한 검증 경로다** — 누르면 실제
   원문 조각과 문서 URL이 나온다
3. **판정이 실패해도 답변과 나머지 UI는 유지된다** — 판정 실패 배지만 남긴다
4. **결정적 판정(인용·거절)과 확률적 판정(근거성)을 같은 모양으로 그리지 않는다.**
   신뢰 수준이 다른 것을 같은 배지로 그리면 사용자가 구분할 수 없다
5. **각 질문이 독립적으로 처리된다는 사실이 화면에 드러난다.** 대화가 쌓이는 UI는
   맥락이 이어진다는 약속으로 읽히는데, 이 제품은 그 약속을 지키지 않는다 (6절). 방법은 구현에서
6. `[결정 필요]` **D6** 모바일 반응형 — 명세의 "완성도" 항목. MVP인지 확장인지는 PLAN에서

## 6. 안 할 것 (비목표)

비목표는 사과가 아니라 **범위가 부풀지 않게 막는 장치**다.

- **로그인·사용자 계정** — 피드백은 브라우저 로컬에만 남는다.
  → 따라서 **배포본에서 타인의 피드백은 수집되지 않고**, "피드백을 축적해 실패 사례를 모으는
  사이클"은 **내 브라우저 범위**에서만 성립한다. 이 한계를 확장 항목으로 부풀리지 않는다
- **서버·백엔드** — 정적 배포. 수집·임베딩은 빌드 시점에 끝낸다
- **문서 자동 동기화** — 코퍼스는 수동 갱신. 대신 **수집 시점을 화면에 표기**한다 (F8)
- **코퍼스 밖 질문에 답하기** — Anthropic API 일반, 다른 AI 도구, 코드 디버깅.
  공식 문서에 있으나 코퍼스에 없는 것도 여기 포함된다
- **대화 맥락 유지(멀티턴)** — 각 질문을 독립 처리한다. 근거 추적이 흐려지기 때문.
  → 단, **그 사실이 화면에 드러나야 한다** (5절 규칙 5). 안 하는 것과 숨기는 것은 다르다
- **다국어 UI** — 한국어 하나

## 7. 못 답할 때의 행동

F4의 3단 상태와 같은 축으로 읽는다.

| 상태 / 상황 | 행동 |
|---|---|
| **근거 약함** | 답하되 **자료의 한계를 명시**하고 경고 배지. 단정하지 않는다 |
| **범위 밖** | 답하지 않고 **이 챗봇의 범위 밖임을 안내**하고, **공식 문서의 다른 페이지에 있을 수 있음을 덧붙인다** |
| 엔진 연결 실패 | 답변 상태와 **분리해서** 표시. **자동 폴백을 하지 않는다** — 어느 엔진의 답인지 흐려지기 때문 |
| 판정 실패 | 판정 배지 자리에 실패 표시. **답변은 그대로 둔다** |

> **정당한 거절은 실패가 아니다.** 근거 없는 걸 지어내지 않은 것이므로 경계가 작동한
> 증거로 센다. 루브릭에서도 그렇게 센다.

## 8. 수용 기준 (배포 전·후 통과할 문)

명세는 "배포 **후** 수용 기준을 정하고, 그 기준으로 동작을 다시 확인"하라고 한다. 그래서
**통과선 수치는 배포 후에 정하되, 지금 쓸 수 있는 실패 조건은 지금 못 박는다.**

### 수용 기준 전용 질문 3개

평가 세트 9개(9절)를 게이트로 쓰지 않는다. **그 9개에 맞춰 튜닝한 뒤 그 9개로 게이트를
통과하면 과적합이다.** 아래 3개는 **실험에 쓰지 않는다.**

| | 유형 | 용도 |
|---|---|---|
| G1 | 정상 (코퍼스 안) | 출처 칩·URL 확인 |
| G2 | 경계 (근거 약함) | 경고 배지 재현 |
| G3 | 범위 밖 (코퍼스에 없음) | 지어내지 않는지 확인 |

> `[결정 필요]` G1~G3의 실제 문장. 코퍼스 확정 후 정한다 (D2에 종속).

### 확인 항목

배포한 URL에서 **직접 실행해** 하나씩 확인한다.

| # | 기준 | 확인 방법 |
|---|---|---|
| A1 | 링크만 받은 사람이 페이지를 열고, 화면 안내대로 최소 준비를 마쳐 질문할 수 있다 † | 다른 브라우저 프로필에서 접속 |
| A2 | **G1** 에서 출처 칩이 뜨고 URL이 열린다 | 클릭해서 실제 문서로 이동 확인 |
| A3 | **G3** 에서 **코퍼스에 없는 사실을 지어내지 않는다** | 답변을 원문과 대조 |
| A4 | **G2** 에서 경고 배지가 실제로 뜬다 | 재현 |
| A5 | 모든 답변에 **판정 배지가 붙는다** (실패 시 실패 표시) | G1~G3 전부 |
| A6 | 피드백을 남기면 **판정 결과와 함께 보인다** | 👍/👎 후 화면 확인 |
| A7 | 스트리밍 중 **취소가 동작한다** | 취소 버튼 클릭 |
| A8 | 첫 방문에서 다운로드가 있으면 **진행률이 보인다** | 캐시 지우고 재접속 |
| A9 | **화면에서 엔진을 전환할 수 있고, 현재 엔진이 항상 보인다** | API ↔ Ollama 왕복 |
| A10 | **답변 화면에 수집 시점이 보인다** | 헤더/근거 모달 확인 |

† **A1의 정직한 범위** — 정적 배포에 API 키를 넣을 수 없으므로(6절 비목표: 서버 없음),
기본 엔진이 API여도 방문자가 자기 키를 입력해야 할 수 있다(D5). 완전한 무설정 접속은
서버가 있어야 가능하고 그건 비목표다. 따라서 A1이 보장하는 것은 **"Ollama 설치보다 훨씬
가벼운 준비"** 이며, 명세는 이 수준을 허용한다(README 안내로 갈음 가능).

### 실패 조건 (측정 없이 지금 확정)

측정하고 나서 넘을 수 있는 선을 그으면 게이트가 아니다. 다음은 수치와 무관하게 배포 실패다:

- **범위 밖 질문에서 지어낸 답이 하나라도 나오면 배포 실패로 본다**
- **출처 칩의 URL이 실제 문서로 가지 않으면 배포 실패로 본다**
- **"공식 문서에 없습니다"라고 답하는 경우가 하나라도 있으면 배포 실패로 본다**
  (코퍼스 밖과 문서 밖을 혼동한 것 — 1·4절)

> `[결정 필요]` **D3** A2·A3의 통과선 **수치**. 배포 후 측정하고 정한다 (명세가 그렇게 요구).

## 9. 평가 세트 · 루브릭 (수용 기준과 다른 물건)

수용 기준은 **나가기 전 통과할 문**, 루브릭은 **통과한 뒤 세팅을 비교할 자**.

**아래 9개는 루브릭 전용이며 수용 기준(8절)에 쓰지 않는다.** 실험 도중 바꾸지 않는다.
아래는 **초안** — 코퍼스 확정 후 근거가 실제로 있는지 확인해 확정한다.

| | 유형 | 질문 초안 | 기대 행동 |
|---|---|---|---|
| Q1 | 정상 | hook은 어떤 파일에 설정하나요? | 근거 있는 답 + 출처 |
| Q2 | 정상 | subagent와 skill은 언제 각각 쓰나요? | 근거 있는 답 + 출처 |
| Q3 | 정상 | 프로젝트 설정과 전역 설정이 충돌하면 어느 쪽이 이기나요? | 근거 있는 답 + 출처 |
| Q4 | 경계 | MCP 서버가 연결이 안 되는데 왜 그런가요? | 코퍼스 범위만, 한계 명시 |
| Q5 | 경계 | CLAUDE.md를 세션 중간에 고치면 바로 반영되나요? | 근거 범위 안에서만 |
| Q6 | 경계 | hook으로 커밋을 막을 수 있나요? | 단정 대신 문서가 말하는 선까지 |
| Q7 | **코퍼스 밖** | Claude Code 요금제가 어떻게 되나요? | **범위 밖 안내** — 공식 문서엔 있으나 **코퍼스 밖임을 구분해** 말한다 |
| Q8 | 문서 밖 | 파이썬 리스트 정렬하는 법 알려줘 | 정당한 거절 |
| Q9 | 문서 밖 | 다음 버전에 어떤 기능이 나오나요? | 정당한 거절 |

> Q7과 Q8·Q9는 **다른 종류의 실패를 잡는다.** Q7에 "공식 문서에 없습니다"라고 답하면
> 그건 정당한 거절이 아니라 틀린 답이다.

### 루브릭 지표

| 지표 | 측정 | 판정 출처 | 관측값 | 비교 기준선 |
|---|---|---|---|---|
| 출처 인용률 | Q1~Q6 중 인용 ID가 유효한 답 수 | **규칙** | `[미측정]` | `[최초 측정값을 기준선으로]` |
| 범위 밖 처리 | Q7~Q9 중 올바르게 범위를 안내한 수 | **규칙 + 사람** | `[미측정]` | `[최초 측정값을 기준선으로]` |
| 근거성 | Q1~Q9 중 근거성 통과 비율 | **LLM** | `[미측정]` | `[최초 측정값을 기준선으로]` |
| 불필요한 거절 | Q1~Q6 중 거절한 수 (낮을수록 좋음) | **규칙** | `[미측정]` | `[최초 측정값을 기준선으로]` |

> "목표값"이라 부르지 않는다. 측정 후에 채우는 값을 목표라 부르면 8절과 같은 함정에 빠진다.
> **최초 측정을 기준선으로 삼고, 세팅을 바꿀 때마다 그 기준선과 비교한다.**

### 판정 신뢰도 스팟체크

**판정으로 시스템을 재는 이상, 판정 자체가 검증되지 않으면 표의 숫자가 근거를 잃는다.**
평가 세트 중 **3개를 사람이 직접 채점**해 LLM 판정과 대조하고 불일치를 기록한다.

> [FINDINGS](FINDINGS.md) 2절에서 확인된 것: 2b 모델은 정답 케이스의 형식은 지키지만,
> **오답·환각을 실제로 잡아내는지는 아직 확인되지 않았다.** 스팟체크가 그걸 메운다.

### 실험 축 — 3개로 축소, 한 번에 하나만

9질문 × 8축 = 72회 실행 + 판정까지 144회 LLM 호출은 로컬 2b로 하루가 사라진다. 명세가
요구하는 것은 "세팅 변화에 따른 성능 차이를 **표로**"이므로 축을 줄이고 하나를 확실히 판다.

1. **top-k** (근거 개수)
2. **약한 근거 임계값**
3. **프롬프트의 인용 규칙 문구**

시간이 남으면 나머지. **코퍼스 언어 축은 없다** — 4절에서 확정했다.

### 실패 분석

실패한 답(틀린 답 · 근거 없는 답 · 불필요한 거절)마다 **어느 단계가 원인인지** 기록한다:
청크 분할 / 임베딩·검색 / 프롬프트 / 생성 / 판정.

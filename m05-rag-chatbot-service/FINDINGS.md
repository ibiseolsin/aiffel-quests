## 2. 판정(LLM-as-a-Judge) — 2B 모델의 JSON 신뢰도

`qwen3.5:2b` / `stream:false` / `think:false` / `temperature:0` 로 같은 입력을 3회 반복.

### 시도 A — `format:"json"` + 프롬프트로 필드 지시 (커리큘럼 방식)

```
grounded / noHalluc / cited / refusal / score / comment
```

**결과: 3회 모두 실패.** 파싱은 되지만 필드명이 어긋난다.

| 문제 | 관찰 |
|---|---|
| 필드명 변조 | `noHalluc` → **`"No Hallucination"`** (3/3 동일. temp 0이라 재현적) |
| 점수 척도 | `score: 10` — 5점인지 10점인지 100점인지 알 수 없음 |

### 시도 B — `format: <JSON 스키마>` 로 스키마 강제

Ollama는 `format` 에 `"json"` 대신 **JSON 스키마 객체**를 받는다.

**결과: 필드명은 3/3 정확. 그런데 의미가 틀렸다.**

| 문제 | 관찰 |
|---|---|
| **부정형 필드를 반대로 판정** | 환각이 없는 답인데 `noHalluc: false` (3/3 동일) |
| `comment` 비어 있음 | `""` — 스키마를 최소로만 만족 |
| 척도 무시 | 스키마에 `maximum:100` 을 줬는데도 `score: 5` |

> 척도 문제는 강의노트가 예고한 것과 일치한다 — "모델이 5점 만점으로 반환하는 경우가 있다".

### 시도 C — 스키마 + **긍정형 필드명** + 필드별 `description` + 이름에 척도 명시

| 바꾼 것 | 어떻게 |
|---|---|
| `noHalluc` → `hallucinated` | 이중부정 제거. "만들어냈으면 true" |
| `score` → `scoreOutOf100` | 척도를 **필드명에** 박음 |
| 각 필드에 `description` | 무엇이 true인지 한 줄로 |
| `comment` 에 `minLength: 10` | 빈 문자열 차단 |

**결과: 2/2 전부 정확.**

```json
{
  "groundedInSources": true,
  "hallucinated": false,
  "citedIds": true,
  "refusedForNoEvidence": false,
  "scoreOutOf100": 95,
  "comment": "답변은 [CC-001 | Hooks 참조] 문맥을 정확히 반영하여 …"
}
```

> 위 예시의 `[CC-001 | Hooks 참조]` 는 **실제로 관측된 출력 그대로**다. 이 프로브는 도메인을
> 바꾸기 전에 돌린 것이라 옛 코퍼스 예시가 들어 있다. 기록을 고치지 않고 그대로 둔다 —
> 실험 기록을 사후에 다듬으면 근거가 아니게 된다. **결론은 도메인과 무관하게 유효하다.**

### 결론 — 판정 슬라이스의 계약

1. **`format` 에 JSON 스키마를 넘긴다.** `format:"json"` 만으로는 필드명이 안 지켜진다
2. **필드명을 긍정형으로 쓴다.** 2B 모델은 부정형(`noHalluc`)의 참/거짓을 뒤집는다
3. **척도를 필드명과 description에 박는다.** 스키마의 `maximum` 만으로는 안 지켜진다
4. **모든 필드에 `description` 을 붙인다**
5. 판정 필드 이름이 강의노트와 달라지지만, **퀘스트 명세는 필드명을 강제하지 않는다**
   ("근거성과 거절 여부 등을 자동 판정") — 의미가 맞는 쪽을 택한다

> 아직 확인하지 않은 것: **틀린 답·환각이 있는 답을 넣었을 때 제대로 잡아내는가.**
> 위 테스트는 정답 케이스 하나뿐이다. 판정 슬라이스에서 오답 케이스로 재확인해야 한다.
> 지금 결과는 "형식이 지켜진다"까지만 증명한다.

**각 호가 자연스러운 사실 단위 청크다.** 단독으로 읽어도 주어와 맥락이 서고, 인용 URL도 있다.

### 확인된 함정 두 개

**① `조문번호` 가 중복된다.** 조의 가지번호가 별도 필드다.

| 조문번호 | 조문가지번호 | 조문제목 |
|---|---|---|
| 8 | (없음) | 부당한 표시 또는 광고행위의 금지 |
| 8 | **2** | 마약류 표시ㆍ광고 영업자 등에 대한 권고 |

표시광고법에서 중복 사례: 제4조 계열 2개, 제8조 계열 2개, **제13조 계열 5개**.
`조문가지번호` 를 ID 에 반영하지 않으면 **청크 ID 가 충돌한다.**

**② 고시의 실제 내용이 `별표` 에 많다.** 응답 최상위 키가
`['별표', '행정규칙기본정보', '조문내용', '첨부파일', '부칙', '제개정이유']` 이고,
「표시기준」 247KB 중 본문보다 별표가 크다. **별표를 빼면 "무엇을 어떻게 적어야 하는가"가
빠진다.**

### 확인된 함정 ③ — **API 의 `[현행]` 이 "지금 시행 중"을 뜻하지 않는다** ★

가장 위험한 함정이다. 오늘은 **2026-08-28** 인데:

| 고시 | 발령 | **시행** | API 플래그 |
|---|---|---|---|
| 식품등의 표시기준 | 2026-05-12 | **2028-01-01** | `[현행]` |
| 유전자변형식품등의 표시기준 | 2026-07-08 | **2026-12-31** | `[현행]` |
| 식품등의 부당한 표시 또는 광고의 내용 기준 | 2025-12-04 | 2025-12-04 | `[현행]` |

`lawService.do?target=admrul&ID=2100000279014` 로 받은 「표시기준」은 `제개정구분명: 일부개정`,
`시행일자: 20280101` 이다. **아직 시행되지 않은 개정본**이다. 부칙에는 기반 고시가
`2019년 10월 28일부터 시행한다` 로 남아 있다 — 즉 **지금 실제로 적용되는 본문은 다른 판**이다.

> **이걸 그대로 코퍼스에 넣으면 이 제품이 가장 하지 말아야 할 실수를 한다.** PRD 1절이 경계한
> "개정 전 기준을 현재로 말함"의 거울상 — **시행 예정 기준을 현행으로 제시하는 것**이다.
> 사용자는 *지금* 판매채널에 등록하는 사람이라 현행 기준이 필요하고, 이 오류는 과징금·회수로
> 직결된다.

법률 쪽은 조문 단위 시행일이 균일했다 (실측):

| 법령 | `기본정보.시행일자` | `조문시행일자` 분포 |
|---|---|---|
| 표시광고법 (269957) | 20250919 | 20250919 × 37개 |
| 동 시행규칙 (267855) | 20241230 | 20241230 × 22개 |

> 단 **검색 결과의 `시행일자` 와 본문 `기본정보.시행일자` 가 어긋나는 경우를 봤다**
> (시행규칙: 검색 20260101 ↔ 본문 20241230). 검색 결과의 날짜를 믿지 말고 **본문에서 읽는다.**

### 해결 방법 — 조사로 확정 (2026-08-28)

**법령: `target=eflaw` 를 쓴다. `target=law` 는 쓰지 않는다.**

| | `target=law` (공포일 기준) | `target=eflaw` (시행일 기준) |
|---|---|---|
| 키 | `MST` = 공포 1건 | `법령ID` (또는 `MST`+`efYd`) |
| `기본정보.시행일자` | 그 공포분 부칙의 시행일 — **오늘과 무관** | 그 스냅샷의 시행일 |

```bash
# 오늘 시행 중인 본문 — efYd 를 주지 않는다 (주면 특정 스냅샷 지정)
curl -s "https://www.law.go.kr/DRF/lawService.do?OC=test&target=eflaw&type=JSON&ID=013475"
# 시행 예정 개정 확인
curl -s "https://www.law.go.kr/DRF/lawSearch.do?OC=test&target=eflaw&type=JSON&LID=013475&nw=2"
#   nw: 1=연혁 2=시행예정 3=현행
```

**실측 차이** — 우리 대상 법령에서 실제로 어긋났다:

| 법령 | `target=law` | `target=eflaw` (정답) |
|---|---|---|
| 식품표시광고법 시행규칙 | 2024-12-30 | **2026-01-01** |

> **이 버그로 처음 수집한 코퍼스는 시행규칙의 낡은 판을 쓰고 있었다.** 잡아낸 경로가
> 리뷰의 함정 ③ 지적이었다.

**고시: 시행일 기준 조회 API 가 없다. 판 목록에서 직접 고른다.**

- `현행여부=Y` / `현행연혁구분=현행` 은 **"가장 최근 발령"** 을 뜻하고 시행 여부와 무관하다
- 판 목록: `lawSearch.do?target=admrul&nw=2&search=1&display=100&query=<고시명>` →
  `행정규칙ID` 로 필터 (판을 묶는 키). 개별 판은 `행정규칙일련번호`
- **고르는 규칙**: `시행일자 <= 오늘` 인 판 중 **발령일자가 가장 늦은 것**
- **`max(시행일자)` 로 고르면 안 된다** — 판이 발령일자 순으로 누적되므로 오래된 본문이 뽑힌다.
  표시기준에서 그러면 발령 2025-04-21 판(부칙 16건)이 뽑히는데 2025-08 개정이 아예 없다

**우리 자료의 오늘 적용 판** (스크립트가 매 실행마다 다시 계산한다):

| 자료 | 오늘 판 | 시행 | API 가 `현행` 이라 부르는 판 |
|---|---|---|---|
| 식품등의 표시기준 | `2100000263558` | 2025-08-29 | `2100000279014` (시행 **2028-01-01**) |
| 유전자변형식품등의 표시기준 | `2100000183336` | 2019-10-28 | `2100000282012` (시행 **2026-12-31**) |
| 나머지 4건 | API `현행` 과 일치 | — | — |

### 확인된 함정 ④ — 조문별 시행일은 `조문단위` 가 아니라 `기본정보` 에 있다

`조문단위[].조문시행일자` 는 **스냅샷 안에서 항상 단일값**이다. 일부 조문만 나중에 시행되는
경우는 `기본정보.조문시행일자문자열` · `별표시행일자문자열` 에만 드러난다.

**구분자가 없다.** 시행규칙 실측값:

```
별표시행일자문자열 = "20241230:별표2,별표720260101:별표2,별표4"
```

`별표7` 과 `20260101:` 이 붙어 있다. `(\d{8})\s*:` 경계로 잘라야 한다.
파서를 소득세법(`20270101:` 포함)으로 검증해 미래분만 걸러지는 것을 확인했다.

우리 대상 법령에는 **미시행 조문·별표가 없다** (전부 오늘 이전 시행).

### 확인된 함정 ⑤ — 고시 본문은 **마커가 앞 단어에 붙어서** 온다

「표시기준」은 조 번호가 없고 본문 전체가 구조 없는 한 문자열로 온다. 그 안의 계층 마커가
앞 단어에 그대로 붙어 있다 — `식품가.` `떡류1)` `제품명나)`. 그래서 청크 분할에서 두 방향의
실패가 동시에 났다:

| 판별 기준 | 무엇이 깨지는가 |
|---|---|
| 앞이 공백일 때만 마커 | 진짜 계층을 통째로 놓친다 (`식품가.` 를 못 본다) |
| 조건 없이 `[가-하]\)` | 「열량 표시 제외)」의 `외)` 가 마커가 되어 **단어가 두 동막** 난다 |

실제 구분자는 공백이 아니라 **순번**이다. 목록은 1부터 순서대로 오르고, `외` 는 순번 글자가
아니며 날짜 「2025. 8. 29.」의 `8.` 은 1로 시작하지 않는다. 순번이 기대값과 맞는 마커만
인정하면 둘 다 해결되고, 계층 혼동까지 같이 막힌다 — 항목 2 안에 든 `1)` 은 기대값(3)과
달라 형제로 오인되지 않는다. 여는 괄호도 배제해야 한다: `(3)` 안의 `3)` 이 형제로 잡히면
위치 표기가 한 칸 틀린다.

함께 고친 것 둘:

- **머리말을 재귀에서 뺀다.** 조각마다 머리말을 붙이고 그 결과를 다시 쪼개면 머리말 자신이
  다음 계층의 마커로 잘려 나간다. 그래서 얼음류 조항이 「과자류」 머리말을 달고 있었다
- **짧은 형제를 묶는다.** 계층 끝까지 쪼개면 「아) 용기ㆍ포장 재질」 같은 11자 조각이 나온다.
  검색에도 안 걸리고 걸려도 근거가 못 된다. 236개가 그랬다

계층으로 못 자르는 덩어리는 마지막에 **문장 경계(「…다.」)** 로 묶는다. 글자 수로 끊지 않는다 —
반토막 난 문장은 근거로 쓸 수 없다.

**결과**: 534 → 365 청크. 최대 4653자 → 1156자, 1200자 초과 0개, 중위 187자.

### 남은 한계 — 정직하게 기록

1. **오늘 시점에 정확히 대응하는 고시 본문은 API 에 없다.** 표시기준의 경우 2025-08-29 판을
   쓰는데, 2026-05-12 발령분 중 즉시 시행된 일부(`Ⅱ.1.너.8)`·표5)가 빠져 있다.
   그 반대(2028년 개정본 사용)는 시행 예정 기준을 현행으로 제시하는 것이라 더 나쁘다
2. **고시 청크 201개 중 66개는 정확한 위치를 못 짚는다.** 위치 표기는 **애매해지는 깊이에서
   멈춘다** — 어떤 계층의 마커가 한 청크 안에 둘 이상 있으면 그 청크는 그 계층의 형제 여럿에
   걸쳐 있다는 뜻이므로, 그중 하나를 위치로 적으면 거짓이 된다. 그 위까지가 참인 가장 깊은
   위치다. 거기까지도 못 읽으면 `본문` 으로 남긴다 — 없는 호 번호를 만들어 내지 않는다.
   형제를 남기고 조상을 접는 것도 금지다: 「나) 식품유형 다) 영업소… 마)」 는 위치가 아니라
   목록의 일부다. 한글 표기는 **순번 글자만** 인정해야 한다 — 그러지 않으면 「…하여야 함.」의
   `함.` 이 표기로 잡혀 위치가 「함.」 으로 나온다. 이 제한을 걸면 위치 불명이 45 → 66개로
   늘지만, **틀린 위치를 적는 것보다 모른다고 하는 쪽이 맞다**
3. 법률에 **2026-11-27 시행 예정 개정**이 대기 중이다. 코퍼스에는 넣지 않았고, 그때 재수집이 필요하다
4. **Q7(수출 라벨)은 키워드만 걸리고 실질 근거가 없다.** 「수출」이 든 청크 5개는 전부 다른
   내용(비방 광고·소분·인삼·정부증명서)이다. 그래서 PRD 9절에서 Q7 을 「일부 범위 밖」에서
   **「코퍼스 밖」** 으로 정정했다. 반대로 **Q2(알레르기)는 근거가 있다** — 「표시기준」에 27개,
   어린이 기호식품 고시에 8개. PRD 가 우려했던 "일반식품 근거 없음"은 해당하지 않는다

## 5. 임베딩 모델 선택 (2026-08-28 실측, S3)

### 배치로 임베딩하면 벡터가 배치 동료에 의존한다 ★

가장 조용한 버그였다. 청크를 16개씩 묶어 임베딩했더니, **같은 청크를 단건으로 다시 임베딩한
벡터와의 코사인이 0.977** 이었다. 같은 모델·같은 글인데 값이 달랐다.

원인은 패딩이다. 배치 안에서 가장 긴 글에 맞춰 짧은 글에 패딩이 붙고, 그것이 mean pooling 에
섞여 들어간다. 즉 **각 청크의 벡터가 같은 배치에 우연히 들어간 다른 15개에 의존한다.**

| 조건 | 저장된 벡터와의 코사인 |
|---|---|
| 16개 배치로 재현 (같은 동료) | 1.000000 |
| 단건으로 재현 | 0.977 |

브라우저는 질의를 언제나 한 건씩 임베딩한다. 그래서 빌드도 **한 건씩** 해야 같은 공간이 된다.
빌드 스크립트 끝에 재현성 자체 점검(단건 재임베딩 코사인 > 0.9999)을 넣어 다시 들어오는 것을 막았다.

> **이 버그는 모델 비교 결과 자체를 오염시켰다.** 오염된 벡터로는 e5-base 가 상위5 적중
> 6/7 이었는데, 고치고 나니 5/7 이었다. 패딩 잡음이 우연히 한 문항을 도와줬던 것이다.
> 측정을 믿기 전에 측정 도구를 검증해야 한다는 사례로 남긴다.

### 모델 비교 — 셋 다 동률, 그래서 크기가 결정했다

청크 365개, 상위 5, 정답 집합은 조문 내용으로 정의 (`scripts/eval-retrieval.mjs`).

| 모델 | 실제 다운로드 | 차원 | 상위5 적중 | Q1 | Q5 | N1(조문번호) |
|---|---|---|---|---|---|---|
| **e5-small q8** | **129MB** | 384 | 5/7 | 19 | **12** | 4 |
| e5-base q8 | 282MB | 768 | 5/7 | 11 | 20 | **1** |
| embeddinggemma-300m q4 | ~205MB | 768 | 5/7 | **8** | 55 | 5 |

(Q1·Q5·N1 은 정답이 상위 5 밖일 때의 **최초 순위**. Q2·Q3·Q4·Q6 은 셋 다 1위)

**계획이 정해 둔 embeddinggemma 를 쓰지 않는다.** 계획은 파일 크기만 재고 검색 품질을 재지
않았는데, 실제로 재 보니 두 배 무거운 모델이 더 낫지도 않았다. 품질이 동률이면 방문자가 첫
접속에서 기다리는 시간이 결정한다.

e5-small 의 유일한 약점은 조문 번호를 그대로 묻는 질문(N1)이고, 그건 **S4 의 BM25 가 잡기로
계획된 바로 그 사례**다. 하이브리드 근거가 실측으로 확인된 셈이다.

> 크기 추정도 틀렸다. FINDINGS 1절에서 「e5-small q8 ≈ 35MB」로 적었는데 실측 129MB 였다.
> q8 은 파라미터 1개당 1바이트이므로 **파라미터 수가 곧 MB 수**다 (118M → ~118MB).

### 동일 공간 검증 — 브라우저에서 0.9992

빌드가 저장한 벡터와 브라우저가 다시 만든 벡터의 코사인이 **0.9992** 다. 1.0 이 아닌 것은
WASM 커널과 네이티브 커널의 수치 차이다. 통과선은 0.99 로 두었다.

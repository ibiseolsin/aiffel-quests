# 구현 전 사전 확인 결과

구현을 시작하기 전에 실제로 실행해서 확인한 것들. **추측이 아니라 관찰된 결과만** 적는다.
실험(세팅 비교표)은 별도 문서로 분리한다 — 여기는 "되는지 안 되는지" 확인용.

> 중"을 화면에 표시해야 한다. → PLAN의 엔진 슬라이스에 반영할 것.

## 2. 판정(LLM-as-a-Judge) — 2B 모델의 JSON 신뢰도

`qwen3.5:2b` / `stream:false` / `think:false` / `temperature:0` 로 같은 입력을 3회 반복.

### 시도 A — `format:"json"` + 프롬프트로 필드 지시 (커리큘럼 방식)

```
grounded / noHalluc / cited / refusal / score / comment
```

**결과: 3회 모두 실패.** 파싱은 되지만 필드명이 어긋난다.

| 문제 | 관찰 |
|---|---|
| 필드명 변조 | `noHalluc` → **`"No Hallucination"`** (3/3 동일. temp 0이라 재현적) |
| 점수 척도 | `score: 10` — 5점인지 10점인지 100점인지 알 수 없음 |

### 시도 B — `format: <JSON 스키마>` 로 스키마 강제

Ollama는 `format` 에 `"json"` 대신 **JSON 스키마 객체**를 받는다.

**결과: 필드명은 3/3 정확. 그런데 의미가 틀렸다.**

| 문제 | 관찰 |
|---|---|
| **부정형 필드를 반대로 판정** | 환각이 없는 답인데 `noHalluc: false` (3/3 동일) |
| `comment` 비어 있음 | `""` — 스키마를 최소로만 만족 |
| 척도 무시 | 스키마에 `maximum:100` 을 줬는데도 `score: 5` |

> 척도 문제는 강의노트가 예고한 것과 일치한다 — "모델이 5점 만점으로 반환하는 경우가 있다".

### 시도 C — 스키마 + **긍정형 필드명** + 필드별 `description` + 이름에 척도 명시

| 바꾼 것 | 어떻게 |
|---|---|
| `noHalluc` → `hallucinated` | 이중부정 제거. "만들어냈으면 true" |
| `score` → `scoreOutOf100` | 척도를 **필드명에** 박음 |
| 각 필드에 `description` | 무엇이 true인지 한 줄로 |
| `comment` 에 `minLength: 10` | 빈 문자열 차단 |

**결과: 2/2 전부 정확.**

```json
{
  "groundedInSources": true,
  "hallucinated": false,
  "citedIds": true,
  "refusedForNoEvidence": false,
  "scoreOutOf100": 95,
  "comment": "답변은 [CC-001 | Hooks 참조] 문맥을 정확히 반영하여 …"
}
```

> 위 예시의 `[CC-001 | Hooks 참조]` 는 **실제로 관측된 출력 그대로**다. 이 프로브는 도메인을
> 바꾸기 전에 돌린 것이라 옛 코퍼스 예시가 들어 있다. 기록을 고치지 않고 그대로 둔다 —
> 실험 기록을 사후에 다듬으면 근거가 아니게 된다. **결론은 도메인과 무관하게 유효하다.**

### 결론 — 판정 슬라이스의 계약

1. **`format` 에 JSON 스키마를 넘긴다.** `format:"json"` 만으로는 필드명이 안 지켜진다
2. **필드명을 긍정형으로 쓴다.** 2B 모델은 부정형(`noHalluc`)의 참/거짓을 뒤집는다
3. **척도를 필드명과 description에 박는다.** 스키마의 `maximum` 만으로는 안 지켜진다
4. **모든 필드에 `description` 을 붙인다**
5. 판정 필드 이름이 강의노트와 달라지지만, **퀘스트 명세는 필드명을 강제하지 않는다**
   ("근거성과 거절 여부 등을 자동 판정") — 의미가 맞는 쪽을 택한다

> 아직 확인하지 않은 것: **틀린 답·환각이 있는 답을 넣었을 때 제대로 잡아내는가.**
> 위 테스트는 정답 케이스 하나뿐이다. 판정 슬라이스에서 오답 케이스로 재확인해야 한다.
> 지금 결과는 "형식이 지켜진다"까지만 증명한다.

## 3. 자료 접근 경로 — 국가법령정보센터 OPEN API (2026-08-28 실측)

`https://www.law.go.kr/DRF/` . `OC=test` 로 정상 응답(`resultCode 00 success`)을 확인했다.

| 엔드포인트 | 용도 | 확인 |
|---|---|---|
| `lawSearch.do?target=law` | 법령명으로 검색 → `법령일련번호(MST)` 획득 | ✅ |
| `lawService.do?target=law&MST=<n>` | 법령 본문 (조/항/호 구조) | ✅ |
| `lawSearch.do?target=admrul` | 행정규칙(고시) 검색 → `행정규칙일련번호(ID)` | ✅ |
| `lawService.do?target=admrul&ID=<n>` | 고시 본문 + **별표** | ✅ |

`type=JSON` 과 `type=XML` 모두 동작. **HTML 파싱이 필요 없다.**

> 참고: `law.go.kr/법령/<법령명>` 을 그냥 `curl` 하면 **1.3KB 껍데기**만 온다 (JS 로 본문 로딩).
> 스크래핑 경로는 쓰지 않는다. API 가 정답이다.

### 인용용 URL

`https://www.law.go.kr/법령/식품등의표시ㆍ광고에관한법률/제8조` → **200 확인.**
조문 단위로 링크가 성립하므로 출처 칩이 조문으로 직접 간다.

### 실사용 전 할 일

`OC=test` 는 테스트용이다. law.go.kr 무료 회원가입 후 본인 `OC`(이메일 아이디 앞부분)를
발급받아 `.env` 에 둔다. **커밋하지 않는다.**

### 구조 — 조 → 항 → 호

`조문단위` 의 필드: `조문번호` · `조문가지번호` · `조문제목` · `조문내용` · `조문시행일자` ·
`조문키` · `항`(중첩) . `항` 안에 `항내용` 과 `호`(중첩), `호` 안에 `호내용`.

**제8조(부당한 표시 또는 광고행위의 금지)** 실측:

- 항 2개. 제1항 아래 **호 10개** — 이게 곧 **금지 광고 유형 10가지**다
- 제1항 제1호: "질병의 예방ㆍ치료에 효능이 있는 것으로 인식할 우려가 있는 표시 또는 광고"
- 제1항 제2호: "식품등을 의약품으로 인식할 우려가 있는 표시 또는 광고"
- 제1항 제3호: "건강기능식품이 아닌 것을 건강기능식품으로 인식할 우려가 있는 표시 또는 광고"

**각 호가 자연스러운 사실 단위 청크다.** 단독으로 읽어도 주어와 맥락이 서고, 인용 URL도 있다.

### 확인된 함정 두 개

**① `조문번호` 가 중복된다.** 조의 가지번호가 별도 필드다.

| 조문번호 | 조문가지번호 | 조문제목 |
|---|---|---|
| 8 | (없음) | 부당한 표시 또는 광고행위의 금지 |
| 8 | **2** | 마약류 표시ㆍ광고 영업자 등에 대한 권고 |

표시광고법에서 중복 사례: 제4조 계열 2개, 제8조 계열 2개, **제13조 계열 5개**.
`조문가지번호` 를 ID 에 반영하지 않으면 **청크 ID 가 충돌한다.**

**② 고시의 실제 내용이 `별표` 에 많다.** 응답 최상위 키가
`['별표', '행정규칙기본정보', '조문내용', '첨부파일', '부칙', '제개정이유']` 이고,
「표시기준」 247KB 중 본문보다 별표가 크다. **별표를 빼면 "무엇을 어떻게 적어야 하는가"가
빠진다.**

```bash
# 법령 검색 → MST 획득

# 본문 (조/항/호)
curl -s "https://www.law.go.kr/DRF/lawService.do?OC=test&target=law&type=JSON&MST=269957"

# 고시 본문 + 별표
curl -s "https://www.law.go.kr/DRF/lawService.do?OC=test&target=admrul&type=JSON&ID=2100000269428"
```

## 조건 (명세 원문 기준)

### 1. 기획 — PRD 작성

PRD에 **최소한** 다음 다섯 가지가 들어가야 한다. PRD를 먼저 쓰고, 그 문서를 기준으로 구현한다.

| 항목 | 답해야 할 것 |
|---|---|
| 문제 정의 | 이 챗봇이 어떤 질문에, 어떤 근거로 답해 주는가 |
| 타겟 유저 | 누가 사용하는가 |
| 핵심 기능(MVP) | 근거 검색·출처 공개·답변 생성·자동 판정 등 반드시 있어야 할 최소 기능 |
| 근거 자료 계획 | 어떤 공개 자료를 수집·저장·처리할 것인가 |
| 화면 구성 | 어떤 페이지/화면이 필요한가 |

### 2. 근거 자료 수집 & 벡터스토어

- 공개 자료를 **출처 URL이 붙은 사실 단위 청크**로 분할
- 청크 JSON 스키마와 ID 규칙 정의 (예: `id`·`url`·`section`·`text`) — 본문만 남기지 않는다
- 임베딩해서 정적 벡터스토어 구축. **브라우저 임베딩 / 미리 계산한 정적 파일 둘 다 허용**
- 첫 방문 다운로드가 있으면 캐시와 진행률 표시로 사용 경험을 지킨다

### 3. RAG 파이프라인

- 질문 임베딩 → 청크 검색. **코사인+BM25 하이브리드 "등, 도메인에 맞는 방식을 고른다"**
- 프롬프트 조립 시 **ID·URL·섹션 정보를 잃지 않고** 전달. 필요하면 시간 컨텍스트 등 규칙 포함
- **로컬 Ollama(`qwen3.5:2b` 등) 또는 API**로 스트리밍 + **취소 가능**
- 답변과 함께 출처를 화면에 공개 (출처 칩·근거 보기 등) — 사용자가 직접 확인 가능해야 함
- 근거가 약하면 함부로 답하지 않고 **자료의 한계나 답변 범위를 안내하는 규칙**

### 4. 판정(Judge) & 피드백

- 근거성·거절 여부 등을 **LLM-as-a-Judge로 자동 판정**하고 답변과 함께 화면에 표시
- **사람 피드백(좋아요/별점 등)** 을 남길 수 있고, 자동 판정 결과와 함께 읽을 수 있어야 함
- 생성 문장이 자연스럽다는 사실과 출처를 가진 답이라는 사실을 **구분해서** 보여 준다

### 5. 실험 & 평가

- **내 도메인의 실제 질문**으로 평가 세트 구성, 직접 설계한 루브릭으로 품질 측정
- 프롬프트 / 검색 방식·가중치 / 근거 개수 등을 바꿔가며 **성능 변화를 표로**
- **실패한 답변**(틀린 답, 근거 없는 답, 불필요한 거절)을 모아 **어느 단계가 원인이었는지** 정리

### 6. 배포

- 정적 앱(GitHub Pages 등)으로 **실제 접속 가능한 URL**
- 다른 사람이 링크만으로 사용해 볼 수 있어야 함
  → 로컬 Ollama를 쓰면 실행 안내와 `OLLAMA_ORIGINS` CORS 설정법을 README에 정리
- 배포 후 **수용 기준**을 정하고 그 기준으로 동작 재확인 (예: 대표 질문 N개 중 근거 있는 답 M개 이상)

## 평가 문항 (채점 루브릭)

| # | 문항 | 상세 기준 |
|---|---|---|
| 1 | 기획 | 자기 도메인의 문제·타겟 유저·근거 자료 계획을 PRD에 명확하게 작성 |
| 2 | 자료·벡터스토어 | 출처 URL이 보존된 사실 단위 청크 스키마 정의 + 임베딩해 검색 가능하게 구축 |
| 3 | RAG 파이프라인 | 검색 → 프롬프트 조립 → 답변 생성 → 출처 공개가 **하나의 흐름**으로 이어지고, 약한 근거 규칙이 있음 |
| 4 | 판정·실험 | 자동 판정 + 사람 피드백 연결, 자기 루브릭으로 세팅 변화에 따른 성능 차이를 **표로** |
| 5 | 배포·확장 | 접속 가능한 URL 배포 + 수용 기준 재확인 + 선택 엔진 비교·검색 고도화 등 **확장 시도** |

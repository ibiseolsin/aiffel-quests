# experiment-01 — 완료된 단계를 접으면 후속 세션이 덜 틀리는가

> **이 파일의 「사전 판정식」 절은 결과를 보기 전에 쓰고 커밋했다.**
> 커밋 순서가 그 증거다 (`git log -- agent-m02-harness-teardown/experiment-01.md`).

- 도구: Claude Code CLI `2.1.259` (헤드리스 `claude -p`)
- 작성: 2026-09-03
- 상태: **실행 완료 (2026-09-07)** · 12셀 · 판정 **기각**

## 1. 불편 장면

**과업**: `aiffel-quests/m05-rag-chatbot-service` 의 슬라이스 구현. 슬라이스 S0~S13 을
세션 하나에 하나씩 맡겼다.

**입력**: 매 세션 고정 프롬프트 —
「`PRD.md`, `PLAN.md` 읽고 슬라이스 N 진행. 끝나면 `PLAN.md` 체크하고 커밋.」

**무엇이 잘못됐나**: 후반 슬라이스로 갈수록 세션이 **이미 폐기된 결정을 현재 규칙으로 읽었다.**
가장 뚜렷한 사례는 로컬 Ollama 동작 여부다. 초기 세션이 「배포본에서 로컬 Ollama 는 안 된다」로
결론 내려 그것을 `FINDINGS.md` 9절과 화면 문구 3곳에 남겼는데, 나중에 실제로 확인해 보니
**「된다」가 답이었다.** 2026-08-30 커밋 `m05: 배포본에서 로컬 Ollama 가 된다 — FINDINGS 9절
결론을 뒤집고 틀린 화면 문구를 고침` 이 그 되돌림이다. 그 사이 세션들은 문서에 남은 옛 결론을
그대로 읽고 화면 문구를 만들었다.

**내가 스스로 만든 대응책이 증거다**: `m05-rag-chatbot-service/PLAN.md:464` 에
「**다음 세션이 잘못 판단하기 쉬운 것 셋**」이라는 절을 손으로 추가해야 했다. 문서가
후속 세션을 오판하게 만든다는 것을 알고 있었고, 문서 안에 경고를 더 넣는 방식으로 막으려 했다.

**규모**: 그 시점 `PLAN.md` 는 **58,097 바이트 / 581줄**이고 한 번도 접힌 적이 없다.
`PRD.md` 35,564 바이트를 더하면 세션이 매번 **93KB** 를 읽고 시작했다. 그중 현재 슬라이스에
해당하는 부분은 수십 줄이다.

## 2. 이 불편이 정말 하네스 기능에서 온 것인가

먼저 의심해야 할 다른 원인들:

| 후보 원인 | 배제·유보 판단 |
|---|---|
| **모델 선택** | 배제 못 함. m05 는 여러 모델 등급이 섞여 돌았다 → 실험에서 **모델을 고정**해 분리한다 |
| **과업 난이도** | 배제 못 함. 후반 슬라이스가 더 어려웠다 → 실험에서 **난이도가 같은 fixture** 를 쓴다 |
| **저장소 상태** | 관련 있음. 코드가 커질수록 읽을 것이 늘었다 → fixture 는 코드를 **3줄 스텁 하나**로 고정한다 |
| **네트워크** | 무관해 보인다. 되돌림은 지연이 아니라 **내용 오류**였다 |
| **내 요청 문장** | **배제 못 한다.** 고정 프롬프트가 「`PLAN.md` 읽고」라고만 했지 「완료 절은 건너뛰라」고 하지 않았다. 이건 하네스가 아니라 **내 지시문의 문제일 수 있다** |
| **문서 자체의 오류** | 관련 있음. 옛 결론이 틀렸던 것이지 문서가 길어서가 아닐 수 있다 |

마지막 둘이 이 실험이 진짜로 다투는 대안 설명이다. 이 실험은 **지시문과 문서 내용을 고정한 채
완료 절 본문의 유무만** 바꿔, 남는 차이가 있는지 본다. 차이가 없다면 원인은 하네스의 컨텍스트
관리가 아니라 지시문이나 문서 내용 쪽에 있다는 뜻이고, 나는 그렇게 적을 것이다.

## 3. 가설

> **완료된 단계의 본문을 접지 않은 채 `PLAN.md` 를 통째로 읽히면, 같은 문서를 접어서 읽힐 때보다
> 후속 세션이 「현재 단계가 폐기한 옛 결정」을 구현하는 빈도가 높아진다.**

**반증 조건**: 두 조건의 통과 수가 같거나 접지 않은 쪽이 더 높으면 가설을 버린다. 그 경우
「접기는 정확도를 위한 조치가 아니라 토큰을 줄이는 조치일 뿐」이라고 결론에 적는다.

이 가설은 **동어반복이 아니다.** 접은 문서에서 옛 결정을 지우지만, **현재 규칙은 두 조건 모두에
완전히 적혀 있다.** 접지 않은 문서도 옛 결정 옆에 「1단계 D2 폐기」라고 명시한다. 문서를 제대로
읽는 에이전트라면 두 조건 모두에서 맞혀야 한다. 틀린다면 그것이 컨텍스트 관리의 효과다.

**셀 순서는 고정 시드(20260903)로 섞는다** — 순서 효과를 제거하되 재현 가능하게.

## 6. 사전 판정식 (결과를 보기 전에 확정)

반복 2회 기준. fixture 당 조건별 통과 수는 0·1·2 중 하나다.

| 판정 | 조건 |
|---|---|
| **지지** | 3 fixture 중 **2개 이상**에서 `folded 통과 수 > full 통과 수` |
| **기각** | 위를 만족하지 못하는 모든 경우. 특히 2개 이상 fixture 에서 `full ≥ folded` 면 명확한 기각 |
| **판정 불가** | 2개 이상 fixture 에서 **양 조건 모두 0/2** (fixture 난이도 문제) 또는 `is_error` 셀이 2개 이상 |

**부수 지표는 판정에 넣지 않는다.**

- **토큰**: `folded` 가 적을 것이 거의 확실하다 — 문서가 짧으니 당연하다. **이것을 가설의 지지
  근거로 쓰지 않는다.** 절감량만 기록한다.
- **승인 횟수**: 헤드리스에는 사람이 누르는 승인 창이 없다. `permission_denials` 는 **0 이 나올
  가능성이 높고**, 그러면 「이 실험은 승인 지표를 재지 못했다」로 남긴다. 대리물임을 숨기지 않는다.
- **시간**: 기록하되 판정에 넣지 않는다. 헤드리스 지연은 네트워크에 크게 흔들린다.

**단일 실행으로 읽지 않는다.** m05 에서 얻은 교훈 그대로다 — 「셀당 1회로 잰 축 차이를 효과라고
쓰지 마라」(`m05/PLAN.md:466`). 파일럿 1회는 **소요 시간·사용량 교정용**이며 판정에 쓰지 않는다.

### 파일럿에서 잡은 계측 결함 (설계를 고친 기록)

첫 파일럿 2셀이 **둘 다 `is_error: True` / `terminal_reason: max_turns`** 로 끝났다.
과업 자체는 맞게 구현했는데, 그 뒤 **결과를 실행으로 확인하려다** `Bash` 가 허용 목록에
없어 거부당했고, `PowerShell` 로, 다시 스크립트 파일로 우회를 반복하며 12턴을 태웠다.
`permission_denials` 가 6·7건인 것이 그 흔적이다.

원인은 하네스가 아니라 **내 실험 설정**이었다. 헤드리스 세션에도 `~/.claude/CLAUDE.md` 가
로드되고 거기에 「**「된다」는 실행해서 확인한 것만 말한다**」가 있다. 규칙은 실행을 요구하는데
실행 도구를 내가 막아 둔 것이다.

**고친 것 (두 조건에 동일하게 적용)**: `Bash` 를 허용 목록에 추가, `--max-turns` 12 → 30.
조작 항목은 그대로 하나다. 이 수정으로 셀당 정가 환산이 **$0.438 → $0.146** 으로 줄었다.

> 첫 파일럿 JSON 2개의 `permission_denials` 에 로컬 절대경로가 들어 있어 계정명을
> `<user>` 로 가렸다 (공개 저장소). 거부 기록 자체는 그대로 남겼다.

> 파일럿 4셀은 **사전 판정식에 넣지 않는다.** 6절에 「파일럿은 소요 시간·사용량 교정용이며

> # 판정: **기각**
>
> **12셀 전부 통과했다.** 접지 않은 21KB 문서를 통째로 읽힌 조건에서도, 접은 3.8KB 를
> 읽힌 조건에서도 에이전트는 폐기된 옛 결정을 구현하지 않았다.

### 궤적이 말해 주는 것 — 못 본 게 아니라 보고 물리쳤다

결과 점수만으로는 「옛 결정을 아예 못 봤다」와 「보고 걸러냈다」를 구분할 수 없다.
`trace.md` 의 최종 응답을 보면 접지 않은 조건의 에이전트가 **현재 결정 번호를 명시적으로
인용**한다.

- f1: 「`make_chunk_id`를 **D7(S15) 규칙대로** `f"{doc}-p{page}-c{idx}"`로 구현했고 …」
- f2: 「PLAN.md **D8(S16) 규칙대로** `emit`을 NDJSON 직렬화 … 마지막 개행 없음 …」
- f3: 「S17 명세대로 `load_config(env)`가 `LLM_BASE_URL`만 읽어 … **옛 이름(`OLLAMA_URL`)**이나
  키 부재 시 `KeyError`를 내도록 …」

f3 이 특히 분명하다. 옛 이름을 **이름까지 대며 거부 대상으로 지목**했다. 폐기 표기(「1단계 D2
폐기」)가 붙어 있는 한, 이 모델은 완료 절 본문이 있어도 현재 규칙을 골라냈다.

### 그래서 접기는 무엇을 사는가

**정확도가 아니라 토큰을 산다.** 입력 토큰 중앙값 10.5% 감소(253,754 → 227,053),
`cache_creation` 만 보면 29.9% 감소. 시간(1.8%)과 턴 수(0%)는 사실상 차이가 없다.

**승인 횟수는 이 실험이 재지 못했다.** 헤드리스에는 사람이 누르는 승인 창이 없고
`permission_denials` 는 12셀 전부 0이었다. 6절에서 그럴 가능성이 높다고 미리 적었고,
그대로 됐다. 대리물조차 못 얻었으므로 **승인 지표는 미측정으로 남긴다.**

### 가설과 다른 결과가 나왔다 — 무엇이 원인 설명을 약하게 만들었나

가설이 기각됐으니 「긴 문서가 후속 세션을 오판하게 만든다」는 내 원인 설명은 **이 조건에서는
지지되지 않는다.** 설명을 약하게 만든 것을 순서대로 적는다.

1. **조작 강도가 실물의 1/3 이다.** 실물 `m05/PLAN.md` 는 완료 : 현재 ≈ 19배(58KB)인데
   fixture 는 5.6배(21KB)다. 7절 반론 5에 미리 적어 둔 위험이 그대로 남았다.
2. **폐기 표기가 너무 친절하다.** fixture 의 옛 결정 옆에는 「1단계 D2 폐기」가 또렷이 붙어
   있다. 실물 m05 에서 문제가 된 로컬 Ollama 결론에는 **그런 표기가 없었다** — 그냥 틀린
   결론이 평범한 사실처럼 적혀 있었다. **내가 재현한 것은 내가 겪은 상황이 아니다.**
3. **과업이 한 함수짜리다.** 실물 슬라이스는 파일 여러 개를 건드리고 앞 슬라이스의 코드를
   읽어야 한다. 문서를 훑는 압력이 fixture 보다 훨씬 크다.
4. **현재 절에 정답 예시가 들어 있다.** `make_chunk_id("hr-guide", 3, 5)` → `"hr-guide-p3-c5"`
   처럼 입출력 예시가 있어 과업이 「명세 해석」보다 「예시 찾기」에 가까웠다.
5. **모델 하나(sonnet)로만 쟀다.** Aider 의 GPT-3.5/GPT-4 사례가 정확히 이 위험이다.
6. **반복 2회는 적다.** 전 셀이 만장일치라 분산 문제가 드러나지 않았을 뿐, 경계에 걸린
   과업이었다면 2회로는 못 읽었다.

**요약하면**: 이 실험이 반증한 것은 「긴 문서가 후속 세션을 오판하게 만든다」 일반이 아니라,
**「폐기가 명시된 21KB 문서는 sonnet 을 한 함수짜리 과업에서 오판하게 만들지 않는다」** 라는
훨씬 좁은 문장이다.

# 에이전트 하네스 개선 실험 — 완료된 단계를 접으면 후속 세션이 덜 틀리는가

- 코스: AI Agent 파해치기_Agt1 — m02 [프로젝트] 에이전트 하네스 톺아보기
- 도구: **Claude Code CLI 2.1.259** (헤드리스 `claude -p`)
- 병목으로 지목한 하네스 기능: **컨텍스트 관리**
- 실행: 2026-09-07, 12셀 (3 fixture × 2 조건 × 2 반복)
- 상세 기록: **[experiment-01.md](experiment-01.md)** · 원자료: [`runs/`](runs/)

> ## 한 줄 결과: **가설 기각.** 12셀 전부 통과해 두 조건의 정확도가 같았다.
> 접기는 **정확도를 사는 조치가 아니라 입력 토큰 10.5% 를 사는 조치**였다.
> 접지 않은 조건의 에이전트는 옛 결정을 **못 본 게 아니라 보고 물리쳤다.**

## 1. 불편 장면

**과업**: `m05-rag-chatbot-service` 의 슬라이스 구현. S0~S13 을 세션 하나에 하나씩 맡겼다.

**입력**: 매 세션 같은 프롬프트 — 「`PRD.md`, `PLAN.md` 읽고 슬라이스 N 진행. 끝나면
`PLAN.md` 체크하고 커밋.」

**무엇이 잘못됐나**: 후반으로 갈수록 세션이 **이미 폐기된 결정을 현재 규칙으로 읽었다.**
초기 세션이 「배포본에서 로컬 Ollama 는 안 된다」로 결론 내려 `FINDINGS.md` 9절과 화면 문구
3곳에 남겼는데, 나중에 실제로 확인하니 **「된다」가 답이었다.** 커밋
`m05: 배포본에서 로컬 Ollama 가 된다 — FINDINGS 9절 결론을 뒤집고 틀린 화면 문구를 고침`
(2026-08-30) 이 그 되돌림이다. 그 사이 세션들은 문서에 남은 옛 결론을 그대로 읽고 화면을 만들었다.

**내가 만든 대응책이 증거다**: `m05-rag-chatbot-service/PLAN.md:464` 에
「**다음 세션이 잘못 판단하기 쉬운 것 셋**」이라는 절을 손으로 추가해야 했다.

**규모**: 그 시점 `PLAN.md` 는 **58,097 B / 581줄**이고 한 번도 접힌 적이 없다. `PRD.md`
35,564 B 를 더하면 세션이 매번 **93KB** 를 읽고 시작했다. 현재 슬라이스에 해당하는 부분은 수십 줄이다.

## 2. 이 불편이 정말 하네스 기능에서 온 것인가 (실험 전 의심)

| 후보 원인 | 판단 |
|---|---|
| 모델 선택 | 배제 못 함 → 실험에서 **모델 고정**으로 분리 |
| 과업 난이도 | 배제 못 함 → **난이도가 같은 fixture** 사용 |
| 저장소 상태 | 관련 있음 → 코드를 **스텁 하나**로 고정 |
| 네트워크 | 무관해 보임. 되돌림은 지연이 아니라 **내용 오류**였다 |
| **내 요청 문장** | **배제 못 함.** 「`PLAN.md` 읽고」라고만 했지 「완료 절은 건너뛰라」고 하지 않았다 |
| **문서 내용 자체의 오류** | 관련 있음. 길어서가 아니라 **옛 결론이 틀렸던 것**일 수 있다 |

마지막 둘이 이 실험이 다투는 대안 설명이다. → **지시문과 문서 내용을 고정한 채 완료 절 본문의
유무만** 바꿔 차이가 남는지 본다.

## 3. 가설 (반증 가능)

> **완료된 단계의 본문을 접지 않은 채 `PLAN.md` 를 통째로 읽히면, 접어서 읽힐 때보다 후속
> 세션이 「현재 단계가 폐기한 옛 결정」을 구현하는 빈도가 높아진다.**

**반증 조건**: 두 조건의 통과 수가 같거나 접지 않은 쪽이 높으면 버린다.

**동어반복이 아닌 이유**: 접은 문서에서 옛 결정은 사라지지만 **현재 규칙은 두 조건 모두에 전문이
있고**, 접지 않은 문서는 옛 결정 옆에 「1단계 D2 폐기」를 명시한다. **두 조건 다 정답이 문서에 있다.**

## 7. 판정: **기각**

**12셀 전부 통과.** 21KB 를 통째로 읽힌 조건에서도 폐기된 결정을 구현하지 않았다.

### 궤적 — 못 본 게 아니라 보고 물리쳤다

결과 점수만으로는 「못 봤다」와 「걸러냈다」를 구분할 수 없어 `trace.md` 의 최종 응답을 봤다.
접지 않은 조건의 에이전트가 **현재 결정 번호를 명시적으로 인용**한다.

- **f3**: 「S17 명세대로 `load_config(env)`가 `LLM_BASE_URL`만 읽어 … **옛 이름(`OLLAMA_URL`)**
  이나 키 부재 시 `KeyError`를 내도록 구현했다」 — **옛 이름을 이름까지 대며 거부 대상으로 지목**

### 접기는 무엇을 사는가

**정확도가 아니라 토큰.** 입력 토큰 중앙값 **10.5%** 감소, `cache_creation` 만 보면 **29.9%**.
시간(1.8%)과 턴 수(0%)는 사실상 차이 없음.

**승인 횟수는 재지 못했다.** 헤드리스에 승인 창이 없고 `permission_denials` 는 12셀 전부 0.
5절에서 그럴 가능성을 미리 적었고 그대로 됐다. **미측정으로 남긴다.**

## 8. 불편의 진짜 원인이 그 하네스 기능이었나 (실험 후 회고)

**아니었을 가능성이 높다.** 나는 「문서가 길어서」라고 지목했지만, 길이를 5.6배 조작해도
정확도는 미동도 없었다. 2절에서 배제하지 못한 두 대안이 그대로 살아 있다.

**가장 유력한 진짜 원인은 「폐기 표기의 부재」다.** fixture 의 옛 결정에는 「1단계 D2 폐기」가
또렷이 붙어 있다. 그런데 **실물 m05 에서 나를 물린 로컬 Ollama 결론에는 그런 표기가 없었다** —
틀린 결론이 평범한 사실처럼 적혀 있었다. **나는 내가 겪은 상황을 재현하지 못했다.**
길이를 조작했지만 나를 물린 것은 길이가 아니라 **문서가 자기 오류를 표시하지 않은 것**이었다.

두 번째 대안도 남는다. 내 고정 프롬프트는 「`PLAN.md` 읽고」라고만 했다. **하네스가 아니라
내 지시문**이 원인일 수 있고, 이 실험은 그것을 시험하지 않았다.

그래서 「접기 규칙」을 정확도 근거로는 쓸 수 없다. **토큰 근거로만 쓴다.**

### 원인 설명을 약하게 만든 것 (감추지 않는다)

1. **조작 강도가 실물의 1/3** — 실물 19배, fixture 5.6배
2. **폐기 표기가 너무 친절** — 실물에는 없던 힌트를 내가 넣었다 (가장 큰 결함)
3. **과업이 한 함수짜리** — 실물 슬라이스는 파일 여럿을 건드린다
4. **현재 절에 입출력 예시가 있어** 「명세 해석」이 아니라 「예시 찾기」가 됐다
5. **모델 하나(sonnet)** — Aider 의 GPT-3.5/GPT-4 사례가 이 위험이다
6. **반복 2회** — 만장일치라 드러나지 않았을 뿐

**이 실험이 반증한 것**은 「긴 문서가 후속 세션을 오판하게 만든다」 일반이 아니라,
**「폐기가 명시된 21KB 문서는 sonnet 을 한 함수짜리 과업에서 오판하게 만들지 않는다」**
라는 훨씬 좁은 문장이다.

## 9. 다시 검토할 조건

**다음 실험에서 바꿀 것 하나 — 폐기 표기를 없앤다.** 길이는 양쪽 21KB 로 **고정**하고,
완료 절의 옛 결정에 「폐기」 표기가 **있는가 없는가**만 조작한다. 그러면 반론 3(길이 vs 옛 문장)이
분해된다. 사전 판정식: 표기 없는 조건이 3 fixture 중 2개 이상에서 통과 수가 낮으면 지지.

이 결론을 **다시 열어야 하는 조건**:

- **모델이 바뀌면** — haiku 같은 하위 등급에서 같은 결과가 나오는지 미확인
- **조작 강도를 실물(19배, 58KB)까지 올렸을 때** — 강도 부족이었는지 확인되지 않았다
- **과업이 여러 파일에 걸치면** — 문서를 훑는 압력이 달라진다
- **문서가 자기 오류를 표시하지 않으면** — 실물이 그랬다. 이게 다음 실험이다
- **원논문을 직접 대조했을 때** — 4절 [학술] 수치는 강의노트를 거쳐 인용했다
- **승인 지표가 필요해지면** — 헤드리스로는 못 잰다. 대화형 세션의 승인 로그가 필요하다

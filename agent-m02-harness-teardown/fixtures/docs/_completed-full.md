
## 1단계 — 코퍼스와 청크 (완료)

- [x] **S1. 저장소 뼈대** — `src/`, `tests/`, `data/` 를 만들고 `pyproject.toml` 로 패키지 경계를
      잡았다. 파이썬 3.13 을 기준으로 두고 의존성은 표준 라이브러리만 쓰기로 했다.
      **D1**: 외부 의존성을 넣지 않는다. 정적 배포 산출물의 크기를 예측 가능하게 두려는 것이고,
      나중에 검색 성능이 부족해지면 그때 다시 본다.
      완료 기준: `python -m pytest` 가 0개 수집으로 통과. 확인함.

- [x] **S2. 원문 수집** — 사내 규정 PDF 12건을 텍스트로 변환해 `data/raw/` 에 넣었다.
      변환 과정에서 표가 깨지는 건이 3건 있었고, 표는 이번 범위에서 빼기로 했다.
      완료 기준: 12건 전부 `data/raw/*.txt` 로 존재하고 빈 파일이 없다. 확인함.

- [x] **S3. 청크 분할** — 문단 경계로 자르고 최대 900자, 겹침 120자.
      처음에는 문장 경계로 잘랐는데 조항 번호가 문장 중간에 끼는 문서가 있어 문단으로 바꿨다.
      **D2**: 청크 ID 는 `{doc}-p{page}` 로 쓴다. 문서 슬러그와 페이지 번호만 있으면 원문을
      다시 찾을 수 있고, 같은 페이지 안에서 청크가 여러 개여도 페이지 단위로 보여 주면
      사람이 읽을 때 충분하다고 판단했다. 예: `hr-guide-p3`.
      완료 기준: 12건에서 청크 534개가 나오고 ID 중복이 없다. 확인함 (중복 0).

- [x] **S4. 청크 메타** — 각 청크에 문서 제목, 페이지, 시행일자를 붙였다. 시행일자가 없는
      문서가 2건 있어 `null` 로 두고 화면에서 「시행일자 미표기」로 쓰기로 했다.
      완료 기준: 534개 전부 메타 3칸이 채워지거나 명시적 `null`. 확인함.

- [x] **S5. 청크 저장 형식** — `data/chunks/` 아래 문서별 파일로 나눴다. 한 파일에 몰아넣으면
      부분 재생성이 안 돼서다.
      완료 기준: 문서 12개 → 파일 12개, 합계 청크 수가 534. 확인함.

> 1단계 회고: 청크 크기를 900자로 고른 근거가 약하다. 600/900/1200 을 재 보지 않았고
> 「문단 하나가 대략 들어간다」는 눈대중이었다. 검색 품질이 문제가 되면 여기로 돌아온다.

## 2단계 — 검색과 출력 (완료)

- [x] **S6. 역색인** — 형태소 분석기 없이 공백·구두점 분리 + 소문자화로 토큰을 만들고
      역색인을 세웠다. 한국어 조사가 붙은 토큰이 따로 세어지는 문제가 있지만, 규정 문서는
      명사구 위주라 실사용 질의에서 크게 어긋나지 않았다.
      완료 기준: 「연차」 질의에 관련 청크가 상위 10 안에 든다. 확인함 (3위).

- [x] **S7. BM25 점수** — k1=1.2, b=0.75 기본값을 그대로 썼다. 튜닝은 하지 않았다.
      완료 기준: 점수가 단조 감소 순으로 정렬되고 동점 처리가 결정적이다. 확인함.

- [x] **S8. 질의 확장 보류** — 동의어 사전을 넣으려다 뺐다. 사전을 사람이 유지해야 하고
      규정 용어가 바뀔 때 같이 바뀐다는 보장이 없다. 다음 단계에서 다시 본다.
      완료 기준: 없음 (범위에서 뺀 결정). 결정만 기록.

- [x] **S9. 결과 출력** — 검색 결과를 파이프라인 다음 단계로 넘기는 형식을 정했다.
      **D5**: 결과는 **JSON 배열 하나**로 출력한다. `json.dumps(rows, ensure_ascii=False)` 로
      한 덩어리를 내보내고 받는 쪽이 `json.loads` 한 번으로 읽는다. 파일이 작고 한 번에
      다 읽는 게 단순해서다.
      완료 기준: 출력이 `json.loads` 로 파싱되고 원래 행 수와 같다. 확인함 (534).

- [x] **S10. 중복 제거** — 같은 문서의 인접 페이지가 거의 같은 문장을 담은 경우가 있어
      본문 해시로 완전 중복만 지웠다. 근사 중복은 손대지 않았다.
      완료 기준: 완전 중복 0. 확인함 (7건 제거, 527개 남음).

> 2단계 회고: 검색 품질을 사람 판단으로만 봤다. 평가 세트가 없어서 「좋아졌다」를
> 수치로 못 쓴다. 3단계에서 평가 세트를 먼저 만든다.

## 3단계 — 엔진 연결과 설정 (완료)

- [x] **S11. 평가 세트** — 질의 9개와 각 질의의 정답 청크 ID 목록을 손으로 만들었다.
      정답이 여럿인 질의가 4개 있어 「상위 5 안에 정답이 하나라도 들면 적중」으로 정했다.
      완료 기준: 9개 질의 전부 정답 청크가 코퍼스에 실제로 있다. 확인함.

- [x] **S12. 기준선 측정** — 적중 7/9. 실패한 둘은 표에 있던 내용을 묻는 질의였고,
      표를 범위에서 뺐으니 코퍼스에 답이 없다. **재현 자료가 없어 미확인으로 남긴다.**
      완료 기준: 적중률이 기록되고 실패 원인이 질의별로 적혀 있다. 확인함.

- [x] **S13. LLM 엔진 연결** — 로컬 엔진에 HTTP 로 붙였다. 스트리밍은 다음으로 미뤘다.
      **D4**: 엔진 주소는 환경변수 `OLLAMA_URL` 에서 읽는다. 로컬 Ollama 를 쓰고 있고
      이름이 무엇을 가리키는지 바로 보이는 편이 낫다고 봤다. 없으면 즉시 오류를 낸다 —
      기본값을 두면 엉뚱한 데로 붙어도 조용히 넘어간다.
      완료 기준: 환경변수가 있으면 붙고 없으면 오류. 확인함.

- [x] **S14. 프롬프트 조립** — 검색 결과 상위 5개를 근거로 붙이고 「자료에 없으면 없다고
      답하라」를 넣었다. 자료 밖 내용을 만들어 내는 건이 줄었지만 수치로 재지는 않았다.
      완료 기준: 조립된 프롬프트에 상위 5개 청크 ID 가 전부 들어간다. 확인함.

> 3단계 회고: 엔진을 하나만 붙여 두고 「엔진 교체 가능」이라고 쓸 수 없다.
